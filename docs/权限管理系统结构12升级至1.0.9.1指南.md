# 权限管理系统结构 12 → 1.0.9.1 升级指南

适用于 Linux x86_64、外部 MySQL 8.x、`docker run` 部署。当前数据库结构已确认为 **12**，目标应用为 **1.0.9.1**、数据库结构为 **13**。示例容器名为 `cli-access`，配置目录为 `/opt/cli-access-config`。实际网络、端口、挂载、代理和 TLS 配置沿用现有部署。本指南只交付更新指导，不代表生产已升级。

本次交付为 GitHub 正式发布工作流测试并核验的更新包，下载前确认 Release 已正式发布。包内已包含对应镜像的版本、源提交、摘要和校验信息。现有应用版本请以旧容器实际标签为准，不根据数据库结构猜测；保留旧镜像及其身份，供回滚核验。

## 1. 核对现状与结构

- 当前数据库结构：**12**；上一正式版 1.0.7.10 同样使用结构 12。
- 目标应用：`cli-access:1.0.9.1`，数据库结构 **13**。
- 已比较上一正式版及目标源码的迁移与模型：新增 `environment_command_denies` 表，保存环境与禁止命令的唯一关系、创建人和时间；`environments` 新增 `command_policy_revision`，初值为 0。
- **必须执行显式迁移**。旧账号、环境、授权、申请、通知及日志应保持不变；初始禁止清单为空，原有命令不会因升级自动禁用。不重新运行 `create-admin`。

在实际 MySQL 库中执行只读查询：

```sql
SELECT version FROM schema_versions;
SELECT COUNT(*) AS admins FROM admins;
SELECT COUNT(*) AS users FROM users;
SELECT COUNT(*) AS environments FROM environments;
SELECT COUNT(*) AS grants FROM user_grants;
SELECT COUNT(*) AS logs FROM cli_call_logs;
SELECT COUNT(*) AS audits FROM audit_logs;
```

确认 `schema_versions` 恰有一行且为 12，记录其余结果，并记录申请、通知和版本策略等实际使用表的数量与关键配置。若不是结构 12，停止，不套用本指南；不得手改结构版本。数据库及表名以实际配置和模型为准。

记录旧容器的镜像、配置挂载、网络和启动参数，确认 `/opt/cli-access-config/service.env` 是当前真实配置。不要输出或分享其中的数据库密码、私钥和 Token。

## 2. 演练、下载与校验

先备份数据库和配置，在**独立测试库**完成恢复演练。演练库必须来自当前结构 12 的备份；使用目标镜像连接演练库，单进程执行第 4.1 节迁移，核对数据并完成第 5 节验收。不得用生产库演练。

从 [v1.0.9.1 Release](https://github.com/mossexplore/platform-cli/releases/tag/v1.0.9.1) 中取得以下文件：镜像归档、`SHA256SUMS`、`manifest.json`、`Docker-upgrade-1.0.9.1.md`、`Docker-runbook.md`、`README.md`、发布说明和 `service.env.example`。将完整文件放入同一目录，不使用 GitHub 的 Source code ZIP 代替镜像。

```bash
sha256sum --ignore-missing -c SHA256SUMS
docker load -i cli-access-1.0.9.1-linux-amd64.tar.gz
docker image inspect --format '{{.Id}}' cli-access:1.0.9.1
docker image inspect --format '{{index .Config.Labels "org.opencontainers.image.revision"}}' cli-access:1.0.9.1
```

所有校验清单文件应在目录中，不能因 `--ignore-missing` 没报错就忽略缺件。镜像配置 ID、版本和源提交须与 manifest 一致，平台应为 linux/amd64。文件 SHA256、Docker image ID 和仓库镜像摘要是不同对象，不能混用。校验不符立即停止。

保留真实 `service.env` 和外部 MySQL。附件示例仅供首次安装参考，**不能覆盖现有配置**。包内不包含 MySQL、Jupyter Server 或生产凭据。

## 3. 维护窗口与最终备份

安排维护窗口，暂停管理台变更及权限检查入口，停止所有旧服务实例和其他写入来源。单实例示例：

```bash
docker stop --time 30 cli-access
```

**停止写入后，现在完成最终数据库备份和配置目录备份。** 记录备份文件位置、哈希和恢复方法；再次核对管理员、人员、环境、授权、日志、审计、申请、通知及策略的数量和关键配置。确认备份可读、恢复演练已通过后才继续。

备份失败立即停止升级，保持维护窗口，不执行迁移。保留旧容器与镜像；后续备份容器名 `cli-access-schema12-backup` 必须尚未使用，若已存在应选择新的明确名称并记录。

## 4. 迁移并切换至 1.0.9.1

### 4.1 单进程显式迁移

确认所有写入仍已停止，最终备份完成且数据库仍为结构 12。使用目标镜像和原配置目录，只启动一个迁移进程：

```bash
docker run --rm -v /opt/cli-access-config:/run/cli-access:ro \
  cli-access:1.0.9.1 python -m app.manage migrate
```

实际部署若使用自定义 Docker 网络访问 MySQL，迁移进程必须加入原网络；TLS 和配置读取沿用当前部署。不要同时运行多个迁移进程，不要启动新旧应用并发写库。MySQL DDL 会自动提交；若迁移中断，先核对备份和实际结构，再单进程重跑，不能跳过失败步骤或修改 `schema_versions`。

完成后在实际 MySQL 库执行：

```sql
SELECT version FROM schema_versions;
SHOW COLUMNS FROM environments LIKE 'command_policy_revision';
SELECT COUNT(*) AS nonzero_revisions FROM environments WHERE command_policy_revision <> 0;
SELECT COUNT(*) AS initial_command_denies FROM environment_command_denies;
SHOW CREATE TABLE environment_command_denies;
```

结构版本必须恰有一行且为 **13**；修订号列存在，旧环境非零修订号数为 0，新表初始行数为 0，环境与命令唯一约束及环境外键存在。旧表数据与最终备份基线一致。不通过则保持停机排查，不能放行。

### 4.2 切换容器

保留停止的旧容器，使用未占用的备份名称：

```bash
docker rename cli-access cli-access-schema12-backup
```

下面启动参数与历史已验证指南一致，实际网络和 TLS 差异沿用原配置：

```bash
docker run -d \
  --name cli-access \
  --restart unless-stopped \
  -v /opt/cli-access-config:/run/cli-access:ro \
  -p 8008:8008 \
  --read-only \
  --tmpfs /tmp:size=64m,mode=1777 \
  --cap-drop ALL \
  --security-opt no-new-privileges:true \
  --log-driver local \
  --log-opt max-size=10m \
  --log-opt max-file=5 \
  cli-access:1.0.9.1
```

示例端口绑定所有网卡，应保留现有网络限制及 TLS/Nginx 配置。使用原管理员账号，不创建新管理员，不覆盖原 `service.env`。

## 5. 验收与放行

保持业务入口关闭，检查健康和日志：

```bash
docker inspect --format '{{.State.Health.Status}}' cli-access
docker logs --tail=200 cli-access
curl --fail --max-time 5 http://127.0.0.1:8008/cli-permission/healthz
```

逐项确认：

- 页面显示权限系统 1.0.9.1；结构为 13，管理员可登录，原人员、授权、申请、通知和版本策略完整。
- 打开有数据的数据看板和数据分析页，页面返回成功，图表 JSON 可解析，计数是数字而不是字符串。
- 使用测试账号执行授权允许和拒绝检查，新调用日志正确落库。
- 在**测试环境或专用验收环境**手动输入 `ml jupyter files upload` 保存，确认该环境返回 `COMMAND_DISABLED`；其他允许命令和其他环境不受影响。解除规则后下一次鉴权放行，审计包含前后清单。
- 禁止命令每行一条完整路径，包含 `ml` 前缀，不填参数或通配符；不会自动展开命令分组，也不会限制终端或 Notebook 内部行为。
- 配合当前 CLI 1.0.9.1，删除本地禁止清单后服务端拒绝仍生效；环境切换、命令树缓存及离线提示正常。旧客户端可以按上报的命令被拒绝，专用提示与策略展示需新 CLI；不修改现有版本准入策略。
- 按原操作方式重启容器，确认挂载配置生效，数据未丢失。

全部验收通过后才恢复业务入口并观察错误日志。受管理 CLI 的鉴权不是平台自身权限的替代；用户修改客户端、关闭鉴权或直接访问 Jupyter 时，强制控制仍需平台/网关配合。

## 6. 回滚

本次 **12 → 13 有结构迁移，没有降级迁移，不能直接回滚旧镜像连接结构 13 的数据库**。

若迁移前停止升级，可在核对数据库仍为完整结构 12 后恢复旧服务。迁移已经开始或完成时，保持入口关闭并停止新服务，保留故障库、日志、新容器和镜像供排查；将维护窗口最终备份恢复到独立回滚库，核对旧配置确实连接该恢复库，再用保留的旧容器参数和镜像启动旧服务。核对健康、管理员登录、原授权和版本策略后才放行。

恢复备份会丢失备份后新增的禁止规则、授权变更、申请、通知、调用日志和审计；恢复前需保存增量并制定补录方案。不得删除生产库冒充回滚，不得手改 `schema_versions`。备份、旧镜像、旧容器及日志保留到观察期结束。
