# Go CLI 客户端重写设计方案

**状态：待审核。** 设计基线为提交 `ad0e811` 的 Python CLI，设计和后续开发使用本地 `codex/go-cli` 分支。审核通过后进入可行性验证。本文中的依赖、性能指标、工期和安装产物均为提案。

## 1. 目标与开发边界

将用户电脑上的 `ml` 重写为 Go 客户端。正式交付目标为 Windows x64，用户使用随包提供的 `ml.exe`，无需在本机安装 Python、Go 或 Node.js。登录仍使用用户电脑上已安装的 Microsoft Edge。Jupyter 的远端 Python Kernel 仍由平台提供。

首个可替换版本以现有 CLI 的命令、配置、输出、平台接口和权限行为为兼容目标。优先降低 Agent 连续调用的启动成本，简化 Windows 安装，交付包中不包含客户端的 Python 源文件或 Go 源文件。可执行文件仍可逆向分析，权限判断、服务端密钥以及必须保密的决策留在服务端。

开发范围包括 Go 客户端、该客户端的测试与 Windows 安装和升级验证，以及对使用手册和正式 Skill 的同步。权限系统、自研 Agent、权限通知助手、平台接口及远端 Jupyter 服务由现有组件继续提供。自研 Agent 后端仍使用原 Python 包及其现有版本搭配。OpenCode、DeepSeek Harness 等场景仅验证其调用现有 `ml` 的方式，无需为各宿主开发插件。macOS/Linux 可用于开发和离线测试，发布这些平台的安装物另行决定。

## 2. 兼容基线

以实际命令注册、现有测试和 [CLI 使用手册](WiseRec%20CLI%20使用手册.md) 为基准。当前 WiseRec 有 106 个公开叶子命令，MLOps 有 77 个。命令组、全局选项和带默认动作的组不计入叶子命令数量，但行为仍纳入兼容契约。

| 类别 | WiseRec | MLOps | 实现范围 |
| --- | ---: | ---: | --- |
| 会话、环境与用户 | 19 | 19 | `context`、`login`、`logout`、`tree`、`history`、`auth`、`access`、`business`、`env`、`user` |
| 训练与实验 | 24 | 13 | `train` 13 个，`mtp` 8 个，`offline` 3 个 |
| 模型、模板、算法仓与服务 | 17 | 14 | `model` 4 个，`resource` 2 个，`deployment` 2 个，`algorithm` 3 个，`service` 6 个 |
| 样本、数据及质量 | 23 | 8 | `sample-task` 3 个，`dataset` 4 个，`featureset` 6 个，`feature-task` 4 个，`quality` 6 个 |
| MEP 配置 | 1 | 1 | `mep config get` |
| Web Studio 与 Jupyter | 22 | 22 | `webstudio` 5 个，`jupyter` 17 个 |
| **合计** | **106** | **77** | MLOps 按显式平台支持表开放 |

MLOps 的 `train list` 继续调用现有 MLOps 列表接口 `/ai/backend/mtp/traintask/queryList`，沿用页大小上限 200。WiseRec 使用 `/ai/backend/modelDev/modelTrain/list`。MLOps 不开放 `algorithm`、`mtp`、`offline`、`sample-task`、`featureset` 和 `quality`。两平台可复用的业务流程共用实现，平台专用协议集中在对应适配器。平台能力从现有 [适配注册表](../cli-python/src/wiserec_cli/adapters/registry.py) 提取。

迁移期间形成一份逐命令兼容清单。每个叶子命令记录完整路径、管理台支持情况、参数位置与别名、默认值、必要前置、请求或本地文件副作用、确认与重试条件、输出样例、退出码和验收用例。单独纳入 `ml history` 默认动作、`--help`、`--version`、`--no-history`、完成脚本和 `--` 后的原样参数等兼容项。新旧行为有分歧时，先通过测试和真实样例确认，再决定沿用或记录为待批准的差异。

## 3. 客户端结构与依赖

在仓库新增独立的 `cli-go/` Go 模块。构建产物为 `ml.exe`。测试阶段可使用绝对路径运行试点二进制，避免覆盖日常使用的 `ml`。

| 职责 | 设计 |
| --- | --- |
| 命令入口 | 用 Cobra 注册命令和参数，统一处理帮助、补全、取消和退出码。显式关闭或适配会改变现有命令树的默认子命令和提示行为。注册阶段只构造元数据，按需初始化业务服务 |
| 命令执行上下文 | 命令执行入口持有取消信号、输入输出及一次调用标识。登录、本地配置和业务操作按实际需求初始化。版本、帮助和仅依赖本地状态的命令无需创建客户端或启动 Edge |
| 配置和本地存储 | 独立处理配置、凭据、业务目录、历史、安装标识、保活和 Web Studio 缓存。文件格式与锁的兼容由该层负责 |
| 权限和 HTTP | 复用 `net/http`、`crypto/tls`、`crypto/x509`、`encoding/json`。权限服务与平台分别配置客户端，业务调用共享可控的连接池，保留权限检查发生的时机 |
| 业务服务和平台适配 | 命令层负责参数、确认、输出，业务服务构造请求和处理响应。仅在协议存在差异时引入 WiseRec/MLOps 适配。大文件使用流式读写 |
| 交互输出 | 表格、JSON、文本、进度和交互统一处理。使用明确验证过的 Unicode 显示宽度和 TTY 判定。Windows 原生终端与重定向均验证 UTF-8 |
| Edge、WebSocket 与安装 | Edge 适配器和 Jupyter WebSocket 客户端各自独立。Windows 安装脚本和发行物位于 CLI 范围内，平台服务无需配套部署 |

Cobra 和面向 Chromium DevTools Protocol 的 Go 库 `chromedp` 为候选。按试点结果选定依赖、锁定版本并审查许可证。WebSocket 库按代理、TLS、握手、取消和帧大小限制的验证结果选择。依赖选择优先支持 Windows x64 原生构建并减少外部运行时。 [Cobra 文档](https://github.com/spf13/cobra) · [chromedp 文档](https://github.com/chromedp/chromedp)

## 4. 请求、权限与错误约定

业务命令按现有流程核对平台支持和本地禁用策略，取得登录账号与当前环境已选业务，实时检查权限，再发送业务请求。批量命令或含多个业务阶段的命令，按 Python 实际检查粒度维护同等权限约束。服务端策略快照供命令树展示，命令执行以实时结果为准。有效的禁用、版本拒绝、异常响应、权限服务连接失败等情况保留现有拒绝行为。

- `businessid` 取自当前环境在 `business.json` 的 `selected.businessId`，核对保存账号与当前登录账号。沿用既有请求所需的 `ai-businessId` 和请求体字段。带业务 ID 的请求体字段逐接口遵循当前协议，不能用一个通用对象覆盖服务端要求的结构。
- 平台入口取当前环境 `api_endpoint`，API 源地址与浏览器管理台入口区分处理。权限服务使用 `access_control.url`，按现有规则生成 `/cli-permission` 下的接口地址，核对环境标识、平台源地址和返回账号。
- 延续真实客户端版本、协议版本、安装标识、命令调用 ID 和单次请求 ID。权限日志沿用完整命令、命令路径及脱敏规则，保留调用前后环境等现有审计含义。返回诊断时过滤 Cookie、CSRF、Token、临时签名链接及敏感报文。
- 分别复现权限服务 `certifi`、`env`、`custom` 三种 CA 模式，以及独立的代理设置。若采用随包公共 CA，按已验证的公共证书集合随包分发。显式处理 `SSL_CERT_FILE`、`SSL_CERT_DIR`、证书来源和优先级，避免 Windows Go 运行时默认信任行为与既有契约产生偏差。
- 只在现有协议允许时重试认证或只读请求。部署、启动、取消、软删除、上传及服务试调等操作的重放条件逐条对照。请求已发出而结果未知时报告不确定状态，沿用现有查询核验和分项失败约定。权限、平台、浏览器和下载使用各自的超时及取消条件。
- 签名下载与业务会话使用分开的 HTTP 客户端。按既有地址校验规则处理签名地址和跳转，平台凭据仅在其授权目标范围内使用。保留下载路径、父目录要求、重名行为和中断后清理语义。

实现依据为 [公共运行时](../cli-python/src/wiserec_cli/runtime.py)、[平台客户端](../cli-python/src/wiserec_cli/client.py)、[权限校验](../cli-python/src/wiserec_cli/access.py) 和 [客户端元数据](../cli-python/src/wiserec_cli/client_metadata.py)。

## 5. 登录、凭据与同机状态

### 5.1 Edge 登录可行性先行

当前 Python 实现使用 Playwright 启动 CLI 专用的 Edge profile，用户完成登录，CLI 根据平台用户信息确认身份，并刷新业务目录。Go 试点考虑通过 CDP 实现等价流程。浏览器进程由本次 CLI 调用管理，调试通道限于本机，优先验证更小暴露面的连接方式。区分用户主动取消、平台登录超时、Edge 缺失、专用 profile 被占用和企业策略拦截。验证码、企业 SSO 及其他交互由用户在 Edge 中完成。 [现有登录实现](../cli-python/src/wiserec_cli/auth.py) · [Microsoft Edge 调试策略](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-policies/remotedebuggingallowed)

Windows 受管环境必须实际验证首次登录、重复登录、过期刷新、`business refresh`、退出重登和两种管理台的业务目录。保留专用 profile 与配置目录的边界，新旧客户端的并行验证使用隔离的测试目录，不共用日常登录缓存。若企业策略阻止候选路线，记录失败场景和影响范围，维持 Python 版使用，提交认证方案供用户决定。不会把带 Python 辅助程序的原型作为 Go 正式替换版。

### 5.2 状态兼容与并发

继续支持现有 Windows 标准用户配置目录 `%APPDATA%\ml`。读取旧数据时保留兼容层，安装成功前先校验配置和可恢复性。涉及敏感文件时，备份由本机当前用户权限保护。

| 状态 | 兼容策略 |
| --- | --- |
| `config.json` | 保留当前 schema、环境配置和原有安装覆盖规则。使用新包配置，保留仍有效的 `current`。缺失、损坏或权限不足时按原有语义报告。继续从配置文件相对目录解析相关路径 |
| `credentials.json` | 兼容现有环境键、账号、旧数字时间戳和带时区字符串。读取有效缓存后按现有规则校验与续期。凭据无法安全复用时要求重新登录，避免误用其他环境或账号 |
| `business.json` | 兼容环境、用户名、目录及 `selected.businessId`。刷新和选择更新采用同目录原子替换。选择仍按真实业务目录校验 |
| 历史、安装标识、权限快照 | 保持现有历史兼容和脱敏语义，复用有效安装标识。权限快照缺失或不匹配时可重新同步 |
| Edge profile、Web Studio 缓存和保活状态 | 按环境储存，Web Studio 继续核对账号和业务。缓存不兼容时重新建立连接。保活切换先停止旧版本拥有的 worker，再由新版本按实际终端所有权接管 |

已确认的产品语义是 **共用同一套本地状态的聊天和终端共享当前环境及其租户选择**。会话 A 切换租户后，会话 B 的后续未指定租户查询使用新选择。此项目不增加按 Agent 会话隔离的状态目录功能。

建议单次命令在开始处理业务时取得当前环境、账号和选择，并在多请求流程内维持该目标。执行写入前复核上下文和授权。用户已确认的目标发生变化时停止提交并重新确认。该处理属于并发边界上的兼容细化，需在设计审核中确认。同一状态文件的写入须通过跨进程锁和原子替换防止丢更新，认证刷新与退出使用状态版本或等价的条件校验，避免旧请求重写新凭据。验证共享状态时包括多个终端和多个 Agent 会话。

保活延续非 TTY 不自动启动、终端归属检查、手动停止及账号/环境绑定。建议通过同一个 `ml.exe` 启动内部 worker，内部入口不作为公开业务命令。升级、回滚与退出仅处理能校验归属的 CLI 进程。 [状态与配置](../cli-python/src/wiserec_cli/config.py) · [凭据存储](../cli-python/src/wiserec_cli/credentials.py) · [业务目录](../cli-python/src/wiserec_cli/business.py) · [保活](../cli-python/src/wiserec_cli/ping.py)

## 6. 操作行为与 Jupyter

| 场景 | 必须保留的行为 |
| --- | --- |
| 本地和跨平台命令 | `env list` 的可见性与授权状态，`ml tree --all` 的平台及禁用标记。帮助和本地上下文可在未登录时查看，在线授权诊断沿用现有前置条件。默认树按各环境实际可用范围显示 |
| 只读和混合操作 | 查询分页与输出结构，测试调用只发送一次。部署预览保留其读请求与输出结构，真正的提交沿用用户确认 |
| 训练与文件流 | 训练启动直接提交，批量取消、软删除和克隆沿用各自的确认及结果处理。历史日志与实例日志保留各自的归档路径、角色作业 ID、分项状态和文件下载语义 |
| Web Studio | 实例查询、启动、停止、默认实例选择和动态连接。缓存绑定当前环境、账号、业务及实例，保留直连与 Web Studio 模式 |
| Jupyter Files | 支持目录、元数据、文本、二进制及已有覆盖选项，校验本地与远端路径边界，保持返回 JSON 和错误格式 |
| Jupyter exec、Notebook | 用已有 Jupyter 服务的 HTTP 和 WebSocket 接口管理 Kernel。对照消息 ID、执行结果、超时、中断、输出截断、Notebook 部分结果和 Kernel 回收。远端执行依赖现有 Python Kernel，本地客户端使用 Go |
| Jupyter Terminal | 保留列表、打开、连接、关闭以及终端尺寸、输入输出、断开和中断语义。仍由 Skill 约束 Agent 对交互终端的使用 |

Jupyter 通道以 [Jupyter 消息规范](https://jupyter-client.readthedocs.io/en/stable/messaging.html) 和 [Jupyter Server WebSocket 协议](https://jupyter-server.readthedocs.io/en/stable/developers/websocket-protocols.html) 为参考，是否采用某个协议变体以现有平台和 Python 客户端的实际兼容测试为准。需要同时验证本机隔离 Jupyter Server、两种平台入口实际提供的连接模式及至少一台 Windows 客户端。

## 7. CLI 与脚本兼容

- 保留原命令、短选项、长选项、默认值、模式、参数校验与主要提示。同一命令的参数顺序、重复选项、`--` 和含空格路径，用 PowerShell 和 CMD 真实验证。补全可更新实现，继续提供现有使用入口。
- JSON 表示保留当前字段名、结构、空值和额外字段，金额或大整数避免精度丢失。表格中首列 ID 宽度固定为 36，不换行、截断或省略，其他长字段优先换行。创建、更新等时间换算成北京时间 `YYYY-MM-DD HH:mm:ss`。JSON 原有字段和值保持其现行语义。
- JSON 或原始日志正文保持 stdout 干净，进度、确认提示和错误写入原有对应流。退出码按命令保留。特别覆盖空结果、用法错误、权限拒绝、确认取消、部分失败和 Jupyter 断连或超时。
- 保留现有交互确认、`--yes` 适用范围和只读预览。命令树各层说明结尾符合仓库无标点规范。使用手册及 `skill/` 在同次客户端变更中同步，速查表重新生成并校验。

## 8. Windows 打包、试装与回滚

1. 试点阶段生成独立 Windows x64 ZIP，提供 `ml.exe`、专用安装说明、校验清单和构建元数据。正式替换候选再补齐安装及卸载入口、初始配置、CLI 手册、正式 Skill 和 `/ml` 入口。Go 编译工具链只装在构建端。
2. 先在独立目录以绝对路径试运行。继续保留正式路径与命令名作为最终替换契约，实际安装后验证 `where.exe ml`、`ml --version`、实际配置路径、UTF-8 重定向和 Agent 入口。迁移前提与需要重新登录的情况写进安装说明。
3. 对全新安装、重复安装、已有 Python 版升级、禁网安装、普通用户权限、PATH 中残留入口、企业证书及失败回滚做验证。安装阶段先准备并校验新产物，成功后才切换启动器。升级备份和恢复均在试验账号下验证，恢复旧启动器和可兼容的本地配置。对不兼容或可能过期的缓存，回滚后重新登录。远端已完成的业务操作不随本机回滚。
4. 发行包优先验证目标 Windows 的企业软件策略、完整性校验和必要的签名方式。清单记录 CLI 版本、构建提交、平台、工具链、文件哈希与依赖信息。检查没有 Python/Go 源文件、真实业务配置、私钥或凭据。Skill、许可和安装说明作为可读资源随包提供。
5. 版本规则继续以 `versions.toml` 为来源。构建时由该来源生成或注入真实 CLI 版本，并验证二进制、兼容协议请求和发行元数据。Go 客户端试点不改其他产品版本、不会把现有 Agent 的已验证 Python 搭配自动改成 Go 搭配。

现有 [正式工作流](../.github/workflows/release.yml) 强制多个组件版本相同，并使用 Python Wheel 构建和校验 Windows 交付物。Go 试点可通过独立的本地或 CLI 专项构建验证产物。到正式交付阶段，需先决定如何将 Go 客户端纳入仓库规定的正式发布门禁。改合同和附件范围需要单独确认，现有多组件发布流程可继续运行。开发在本地 `codex/go-cli` 推进，按 [仓库规则](../AGENTS.md) 只向 `main` 推送。正式替换须另行确认，不把试点 ZIP 当作正式安装包。

## 9. 测试方法与验收

| 验证 | 方法及通过条件 |
| --- | --- |
| 命令覆盖 | 用 Python CLI 提取的命令清单逐项比对，WiseRec 106 个、MLOps 77 个全部可执行且门禁一致。覆盖别名、参数、帮助、组默认行为和命令树说明 |
| 接口对照 | 用脱敏固定样例和 HTTP 测试服务分别驱动 Python 与 Go，比较请求方法、路径、关键头、查询参数和 JSON。只归一化 UUID、时间和临时路径等动态值。有副作用的接口先在模拟环境验证 |
| 输出对照 | 比较 stdout、stderr、退出码和文件结果。JSON 以语义为主，原始日志和必要脚本输出逐字节比较。验证首列完整 ID、北京时间、Windows UTF-8 和表格换行 |
| 权限与并发 | 模拟禁用、版本拒绝、权限服务超时、认证失败及 CA 错误，断言业务请求未发送。验证共享租户切换、进行中写入的目标核对、大文件中断、新旧缓存兼容和同机状态文件并发 |
| 真实联调 | 在已授权的非生产环境验证 Windows Edge 登录、两种平台的只读查询、日志归档和受控写操作，以及 Web Studio/Jupyter。写操作使用明确授权的测试资源 |
| 交付 | 在可重置 Windows x64 环境验证安装、无 Python/Go/Node.js 情况下运行、禁网安装、旧版升级及回滚。验收同时覆盖一轮普通终端和一轮 Agent 调用 |

性能测试采取同一台目标 Windows 机、同一客户端配置和同一套测试接口，分别测冷启动和缓存预热后的新进程。每个场景至少 30 次，记录 P50、P95、内存和包体积。测量项包括 `--version`、`context --json`、`tree`、已缓存认证的查询、Agent 连续 10 次调用，以及浏览器登录各阶段。记录进程启动、配置解析、认证、实时权限请求、平台请求和输出各段耗时。人手输入验证码或完成 SSO 的等待单独记录。

**试点性能目标待审核。** 建议本地轻量命令的 P50 比同机 Python 基线下降至少 50%，P95 同步改善。查询的端到端耗时按分段结果评估，实时鉴权次数和确认流程保持兼容。现有 macOS 测量只用于说明启动开销存在，Windows 基线由试点阶段重新采集。
