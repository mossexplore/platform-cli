# 权限管理系统 1.0.3 → 1.0.3.1 升级指南

适用于 Linux x86_64、外部 MySQL 8.x、`docker run` 部署。示例沿用容器 `cli-access`、配置目录 `/opt/cli-access-config` 和端口 8008；实际网络、端口、挂载、TLS 和代理配置应按现有部署保留。本文是操作指导，不代表生产升级已执行。CLI 也更新至 1.0.3.1，按新版 Windows 安装包升级客户端；原有业务和权限配置应在升级前备份并核对。

## 1. 确认版本与结构

- 上一正式权限镜像：`cli-access:1.0.3`，数据库结构 **8**。
- 目标权限镜像：`cli-access:1.0.3.1`，数据库结构 **10**。
- 8 → 9 为 `admins` 新增 `display_name VARCHAR(128) NOT NULL DEFAULT ''`；9 → 10 为 `cli_version_policies` 新增可空 `deleted_at DATETIME`。现有姓名为空，现有策略均未删除；密码、角色、授权、审计、日志保持原样。
- 目标服务健康检查要求结构 10。启动不会自动迁移；不能同时运行新旧服务访问同一数据库。

先核对生产库 `SELECT version FROM schema_versions;` 恰有一行且为 8，核对实际列与标记一致。若结构不是 8，停止并按真实结构制定迁移方案，不手改版本号。

## 2. 演练和备份准备

记录现用镜像 ID、配置目录、容器参数、数据库地址、网络与端口，保留旧镜像和原配置。完整备份权限系统数据库及配置目录，并在**独立测试库**真实恢复；用目标镜像指向测试库迁移，核对管理员账号、密码哈希、角色、人员、授权、历史日志和策略行数，确认新增列与重复执行迁移均正常。测量迁移耗时和锁等待，安排维护窗口。

数据库账号需有 SELECT、INSERT、UPDATE、DELETE、CREATE、ALTER、INDEX 等权限。备份文件和 `docker inspect` 输出可能包含凭据，只交由授权运维保管。演练通过后才允许生产停写。真实 `service.env` 必须保留，不能用附件示例覆盖。

## 3. 下载并独立检查目标镜像

从 v1.0.3.1 正式 Release 下载 `cli-access-1.0.3.1-linux-amd64.tar.gz`、`SHA256SUMS`、`manifest.json` 和本指南。先在可信机器核对 `SHA256SUMS` 覆盖所需附件，且校验结果均为 OK，再导入镜像：

```bash
sha256sum --ignore-missing -c SHA256SUMS
docker load -i cli-access-1.0.3.1-linux-amd64.tar.gz
docker image inspect --format '{{.Id}}' cli-access:1.0.3.1
docker image inspect --format '{{index .Config.Labels "org.opencontainers.image.revision"}}' cli-access:1.0.3.1
```

确认镜像配置 ID 和源码提交对应 `manifest.json` 的 `image_id`、`image_revision`。文件 SHA256、Docker image ID、仓库镜像摘要是不同对象。任一核对失败应停止升级。

## 4. 维护窗口停写与最终备份

暂停管理台变更与权限检查入口，停止**全部**旧实例和其他写入来源。单实例示例：

```bash
docker stop --time 30 cli-access
```

**停止后现在做最终数据库备份和配置目录备份，并记录各表行数、关键 ID、授权有效期和策略状态。** 确认备份可用于恢复后，才进入下一节。不要以数小时前的在线备份代替最终恢复点；不要在迁移前删除旧容器或旧镜像。

## 5. 单进程显式迁移

确认挂载目录中的 `service.env` 指向目标数据库，若旧部署使用 Docker 网络，为迁移容器加入同样网络参数。只启动一个迁移进程：

```bash
docker run --rm \
  -v /opt/cli-access-config:/run/cli-access:ro \
  cli-access:1.0.3.1 python -m app.manage migrate
```

预期成功输出“数据库初始化完成（版本 10）”。随后核对 `schema_versions` 恰有一行且为 10，`admins.display_name` 和 `cli_version_policies.deleted_at` 存在；旧管理员、授权、日志、审计与策略的数量和关键值符合基线。历史管理员姓名应为空、历史策略 `deleted_at` 应为 NULL，不得据此补造身份或删除历史。

MySQL DDL 可能在中途自动提交。失败时保持停机并检查实际结构；迁移代码按列检查，可在排障后重复执行，但不能并发迁移、删除业务表或手改 `schema_versions` 冒充成功。

## 6. 切换镜像与验收

迁移和数据核对成功后，保留已停止的旧容器，给它一个未使用的备份名称；若名称已占用，先查明归属。沿用实际网络、端口及配置挂载，单实例示例：

```bash
docker rename cli-access cli-access-1.0.3-backup
```

```bash
docker run -d \
  --name cli-access \
  --restart unless-stopped \
  -v /opt/cli-access-config:/run/cli-access:ro \
  -p 8008:8008 \
  --read-only \
  --tmpfs /tmp:size=64m,mode=1777 \
  --cap-drop ALL \
  --security-opt no-new-privileges:true \
  --log-driver local \
  --log-opt max-size=10m \
  --log-opt max-file=5 \
  cli-access:1.0.3.1
```

端口示例绑定所有网卡，需保留现有访问限制；Nginx、TLS、证书、网络等按原部署参数调整。旧容器不能启动到已迁移的结构 10 库。不要运行 `create-admin`，也不要新建数据库。

保持业务入口关闭，核验容器健康、日志及权限行为：

```bash
docker inspect --format '{{.State.Health.Status}}' cli-access
docker logs --tail=200 cli-access
curl --fail --max-time 5 http://127.0.0.1:8008/cli-permission/healthz
```

原管理员登录应正常；人员、环境、授权及历史记录应保留；允许和拒绝的权限检查应符合预期并写入新日志。确认“数据看板”“调用日志”“操作审计”“管理员管理”“版本管理”页面，检查历史姓名为空的展示，以及只有已停用策略可删除。重启服务后再次检查健康和配置读取。全部放行后恢复业务入口并观察数据库负载和错误日志。

## 7. 回滚和数据恢复

- 尚未迁移时：旧库未变，可恢复旧镜像和原容器。
- 迁移已开始或结构已为 10 时：**不能仅切回 1.0.3 镜像**。旧版健康检查要求结构 8；没有自动降级迁移。
- 保留故障库以供取证，停新服务后将最终备份恢复到**独立回滚库**，使用旧镜像、旧配置副本指向该库，核验后才重新开放入口。核对所有回滚配置确实指向回滚库，避免旧服务误连结构 10 的原库。
- 从最终备份恢复会丢失备份后的新增日志、审计或配置变更；先保存这些新增数据并制定补录方案。禁止通过手改 `schema_versions` 冒充回滚。

保留旧镜像、备份和故障日志直至观察期结束。发布 Release 不会自动连接、迁移或替换生产系统。
