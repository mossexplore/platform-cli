# 云侧 Agent 方案设计

面向 WiseRec 平台的云侧 Agent：在服务器部署一个智能体，通过复用现有 `ml` CLI 的能力，让用户用自然语言查询和操作平台资源。

适用源码版本：`wiserec-cli 1.0.3`；权限服务数据库结构版本：`8`。本文档为方案设计，不代表已实现。

---

## 1. 结论

**可行，且本项目的基础条件优于多数同类场景。**

判断依据：

| 条件 | 本项目现状 | 对云侧 Agent 的意义 |
| --- | --- | --- |
| 统一命令入口 | `ml`（Typer），覆盖查询与操作 | 工具面天然收敛，无需逐个封装平台接口 |
| 机器可读输出 | 部分命令支持 `-o json` | 降低 LLM 解析成本，但仍需补齐一致性 |
| 权限与授权 | 权限服务（账号＋环境授权） | 治理层已有，不必从零建设 |
| 版本准入 | `X-CLI-Version` 策略、观察/提醒/强制 | Agent 统一升级，比分散客户端更易强管控 |
| 网关集成点 | `POST /cli-permission/api/v1/gateway/check`＋服务端密钥 | 可直接复用为 Agent 通道的准入检查 |
| 调用审计 | `CallLog`（命令、账号、环境、业务、版本、安装实例） | 审计闭环已成，只需新增入口来源 |
| 业务分层 | `src/wiserec_cli/services/` 已是独立业务层 | 长期可用库调用替代进程调用 |

**真正的难点不在"让 Agent 调用 CLI"，而在"Agent 用什么身份调用平台"。**

CLI 当前的凭据来自交互式浏览器登录：通过 Playwright 拉起本机 Edge，从 `/ai/user/info` 请求头捕获 `cookie` 与 `csrftoken`，缓存到 `credentials.json`（有效期 1800 秒）。这是**用户会话凭据**，不是服务凭据。云侧没有用户的浏览器会话，这构成了本方案的核心约束。

## 2. 业界方案调研

云侧 Agent 的通用骨架已有成熟范式，可归纳为五类：

| 类别 | 代表方案 | 可借鉴之处 |
| --- | --- | --- |
| **工具协议层** | MCP（Model Context Protocol） | 把 CLI 包装成 MCP Server："CLI 是真相来源，MCP 只做翻译层"。支持 stdio（本地）与 HTTP＋OAuth 2.1（远程） |
| **Agent 沙箱执行** | Claude Code、Codex Cloud 的容器化运行 | Agent 在受控容器内执行工具，宿主与执行环境边界清晰 |
| **托管 Agent 运行时** | AWS Bedrock AgentCore、LangGraph Platform、Dify／Coze | 会话、记忆、追踪、伸缩由平台托管 |
| **工具／模型网关** | Kong AI Gateway、LiteLLM Proxy | 统一准入、限流、路由、审计，与现有权限服务定位一致 |
| **Agent 即工具（子 Agent）** | MCP 的 sub-agent 模式 | 主 Agent 委派子 Agent，隔离上下文，按业务域拆分 |

### 2.1 行业共识

1. **CLI 正在成为 AI 的首选工具接口。** 模型可直接调用命令行工具；相较 GUI 自动化，CLI 稳定且可组合。前提是 CLI 具备 `--json` 输出与无副作用的结构化命令。
2. **薄包装优于深度改造。** "Thin MCP wrapper"是主流甜点区：每个工具调用 CLI 子命令并解析输出，约 50–100 行代码，CLI 与工具定义在 CI 中同步验证。
3. **远程 MCP 需要 OAuth。** 从本地 stdio 走向托管服务时，认证故事是前提——服务端必须知道"谁在请求、请求了什么、访问了什么"。
4. **工具描述质量决定 Agent 效果。** Agent 依据工具描述决定何时调用，描述含糊会导致误调用。
5. **凭证必须是短期、按次、限定作用域的。** 下列三条是 2026-09 核实的实施依据，对应到本项目的具体落点见 3.2 与 3.5。

### 2.2 可直接对标的实施依据

| 来源 | 具体做法 | 本项目的落点 |
| --- | --- | --- |
| **AWS Bedrock AgentCore Identity** | 明确区分三种凭证模式：M2M（`client_credentials`，Agent 以自身身份行动）、**On-Behalf-Of（RFC 8693 Token Exchange，代表用户行动）**、User-delegated（授权码三步 OAuth，用户先交互授权）。核心主张是"把授权执行下沉到基础设施层，而不是给 Agent 宽泛凭证再靠应用层过滤" | 写操作应对标 OBO 模式；数据范围由凭证本身限定，边界在服务端强制，不依赖 Agent 自觉 |
| **MCP 2026-07-28 规范** | 远程 MCP Server 强制成为 OAuth 2.1 资源服务器；引入 Resource Indicators（RFC 8707，令牌绑定唯一受众，防跨服务重放）与 Issuer Validation（RFC 9207），专项收敛 confused deputy 攻击面；EMA 扩展通过 ID-JAG 令牌交换免除逐个应用的 OAuth 授权 | 3.5 节所述服务端信任上报 `username` 的现状缺陷，应按此修复 |
| **Claude Agent SDK 部署指南** | 容器沙箱为默认要求，每会话独立生命周期；推荐 **Credential Proxy** 模式——在 Agent 边界之外注入凭据，Agent 自身永不持有长期密钥，代理同时执行 endpoint allowlist 与流量审计 | Agent 容器内不落任何长期凭据；凭据注入统一由网关侧代理完成，网络默认受限 |

### 2.3 业界方案没有解决的问题

上述方案提供的是**编排、执行、治理**骨架，**身份委派问题需自行解决**。这正是本项目可行性的分水岭：平台身份层是否支持非交互式委派。

## 3. 方案设计

### 3.1 总体架构

```
用户（Web 聊天 / 企业微信 / IM / API）
        │  SSE / WebSocket
┌───────▼────────────────────────────────────────┐
│ 接入层    会话管理 · 用户鉴权 · 限流 · 流式回传      │
└───────┬────────────────────────────────────────┘
        │
┌───────▼────────────────────────────────────────┐
│ Agent 编排层   LLM · 规划 · 工具选择 · 记忆 · 追踪   │
└───────┬────────────────────────────────────────┘
        │ 结构化工具调用（非自由文本）
┌───────▼────────────────────────────────────────┐
│ ml-tool 网关（本方案核心，新增组件）                  │
│  ├ 命令注册表   白名单 + 参数 JSON Schema           │
│  ├ 身份解析     用户身份 → 平台凭据（凭据层）          │
│  ├ 授权预检     复用 /gateway/check                │
│  ├ 执行器      固定 argv · 无 shell · 超时 · 并发上限  │
│  ├ 输出规范化  ANSI 清理 · JSON 提取 · 截断 · 摘要    │
│  └ 审计        CallLog，新增 check_source='agent'  │
└───────┬────────────────────────────────────────┘
        │  subprocess（P0） / 库调用（P2）
┌───────▼──────────────┐   ┌──────────────────────┐
│ ml CLI（复用）        │   │ 权限服务（复用）        │
│ wiserec-cli 1.0.3    │──▶│ 授权 · 版本策略 · 日志   │
└──────────────────────┘   └──────────────────────┘
        │
┌───────▼────────────────────────────────────────┐
│ WiseRec 平台 API（cookie + csrftoken + businessid）│
└────────────────────────────────────────────────┘
```

**关键设计原则：Agent 不绕过权限服务。** 每次工具调用前，以真实用户身份向权限服务做一次授权检查，与 CLI 现有预检查保持一致；权限服务的判定结果决定是否执行。

### 3.2 身份与凭据方案（核心决策点）

三个选项，按落地难度与安全强度排列：

#### 方案 A：非交互式凭据委托（目标态，需平台配合）

平台提供 OAuth 2.0 授权码模式或专用 token 交换接口，用长期凭据换取平台会话。

- **优点**：符合平台身份模型；可撤销、可审计；无浏览器依赖；并发成本低。
- **缺点**：需要平台侧改造，周期最长。
- **依赖**：平台认证团队支持。建议尽早启动沟通。

#### 方案 B：服务端浏览器会话池（可快速落地，无需平台改造）

服务端以 Playwright ＋ 虚拟显示（Xvfb／无头模式）为每个用户维护独立的持久浏览器 Profile。

- **优点**：复用现有 `BrowserAuthenticator` 的"持久浏览器会话"复用逻辑（`auth.py` 已实现：优先复用已有会话，失效才要求重新登录）；`config.browser.profile_root` 已支持自定义根目录，天然支持按用户隔离。
- **缺点**：运维复杂；每用户一个浏览器实例，资源成本高；SSO 若含人机校验会阻断自动登录；服务端持有用户会话凭据的合规风险需评估。
- **注意**：`ml login` 依赖系统安装的 Microsoft Edge（不需要 `playwright install chromium`），服务端需预装 Edge 或适配 Chromium 通道。

#### 方案 C：服务身份 ＋ 用户级授权叠加（最快，风险最高）

平台为 Agent 分配一个服务账号并授予所需权限，Agent 侧自行做"用户 → 可执行命令／环境／业务"的映射。

- **优点**：落地最快，无浏览器依赖。
- **缺点**：平台侧看到的都是服务账号，**平台原生权限体系被绕过**，授权仅绑定账号与环境的模型失效。必须配套严格白名单与全量审计。
- **适用**：仅建议用于 POC 或严格只读场景，不作为长期方案。

#### 方案 D：用户主动推送凭据（最轻量 MVP）

用户本地 `ml login` 后，通过新增的 `ml auth push --server <url>` 把当前 `cookie`／`csrftoken` 加密推送到 Agent 服务的注入接口（短期口令或一次性链接校验），服务端按用户隔离存储。

- **优点**：改动最小；服务端零浏览器依赖；凭据仍是用户本人身份，权限与审计语义不变。
- **缺点**：受 1800 秒 TTL 限制，到期需重新 push；适合低频查询或演示验证，不适合常驻高频使用。
- **定位**：比方案 B 更轻的验证手段——用它先跑通「自然语言 → 工具调用 → 真实数据」全链路，再决定是否投入方案 B 的会话池。

#### 推荐路径

| 阶段 | 身份方案 | 说明 |
| --- | --- | --- |
| P0 | 方案 D 或方案 B（小范围试点） | 方案 D 成本最低，先验证价值；需要常驻免维护时上方案 B |
| P1 | 方案 B 强化 ＋ 凭据加密 | 多用户凭据池、KMS 信封加密、TTL 与轮换 |
| P2 | 方案 A 替换 | 平台 token 交换上线后退化掉浏览器依赖 |

**若平台侧短期内无法支持方案 A，且无法接受方案 B 的运维成本，则应把范围收敛到只读查询 + 少量固定用户，不开放写操作。**

### 3.3 Agent 侧对 CLI 的最小改造需求

现有 CLI 已可被调用，但有几处契约缺口会直接影响 Agent 可靠性。以下为**建议改造项**，按优先级排序：

| 优先级 | 改造项 | 原因 |
| --- | --- | --- |
| P0 | **纯 JSON 输出模式** | 文档已承认："其他数据命令在触发认证刷新时仍可能向 stdout 打印提示……不能对所有 `-o json` 命令假定 stdout 始终是纯 JSON"。建议新增 `--machine` 或 `ML_OUTPUT_MODE=machine`，强制所有人类提示走 stderr，stdout 只输出 JSON |
| P0 | **非交互强制模式** | `ml business use`、`ml train start`、`ml offline experiment clone` 存在交互提示。需 `--yes`／`ML_NONINTERACTIVE=1`，缺失时以退出码失败而非挂起等待 |
| P0 | **`-o json` 覆盖统一** | `env`、`auth status`、`business show` 固定表格；`business list` 输出层级目录。Agent 需要一致的结构化输出 |
| P1 | **命令自描述** | 新增 `ml schema --json`，输出命令树与参数 JSON Schema，供 Agent 动态生成工具定义，避免手工维护工具清单与 CLI 漂移 |
| P1 | **调用来源标识** | CLI 已有 `X-CLI-Invocation-ID`／`X-CLI-Installation-ID`。建议新增来源标记，让权限服务调用日志区分人工调用与 Agent 调用 |
| P2 | **服务层作为库暴露** | `src/wiserec_cli/services/` 已是独立业务层，`PlatformClient` 也是干净的独立类。Agent 可直接 `import` 而非 `subprocess`，彻底消除输出解析问题，并支持并发 |

> P2 是长期最优解：库调用可获得结构化输入输出、无 stdout 污染、无进程开销、可精确控制并发。代价是需要把 `CredentialStore` 从文件级实现抽象为可插拔接口，以便按用户注入凭据。

### 3.4 命令分级与执行策略

按风险对命令分级，决定 Agent 的自主程度：

| 级别 | 范围 | 示例命令 | Agent 策略 |
| --- | --- | --- | --- |
| **L0 只读** | 查询类 | `env list`、`business list`、`mtp swanboard *`、`train list`／`instance list`／`history list`、`featureset *`、`offline experiment list`、`user info` | 直接执行 |
| **L1 低风险写** | 可逆或影响局部 | `train config update`、`train history logs download`、`offline experiment clone --dry-run` | 执行前输出计划，需用户确认 |
| **L2 高风险** | 触发计算资源或创建生产资源 | `train start`、`offline experiment clone`（实执行）、`webstudio login`、`jupyter run` | 强制人工确认（HITL），默认拒绝自动执行 |

配合命令注册表：每个工具显式声明 `tier`、参数 Schema、是否支持 `--dry-run`。未知命令一律拒绝，**不采用前缀通配放行**。

**执行方式的选择：进程调用仅适用于 P0。** 每起一次 `ml` 进程都需要重新初始化 Typer、httpx、rich，并重新读取 `config.json`／`credentials.json`／`business.json`，开销在数百毫秒量级；多轮对话调用几十次时累积延迟显著。这也是演进路线中 P2 改为服务层库调用的主要动因——`src/wiserec_cli/services/` 已是不依赖终端输出的独立业务层，改造时 `CredentialStore` 需抽象为可插拔实现。

### 3.5 安全与治理设计

| 关注点 | 措施 |
| --- | --- |
| **凭据隔离** | `cookie`／`csrftoken` 绝不进入 LLM 上下文；仅在工具执行器进程内使用；存储采用 KMS 信封加密；日志脱敏可复用 `invocation.py` 的 `_SECRET` 正则逻辑 |
| **命令注入** | 使用固定 `argv` 列表 + `shell=False`；参数经 JSON Schema 校验；不拼接 shell 字符串 |
| **Prompt Injection** | CLI 返回内容一律视为**不可信数据**，不作为指令；工具选择仅由用户意图驱动；禁止将命令输出回灌为系统提示 |
| **Confused Deputy（服务端混淆代理人）** | **现状缺陷，须优先修复**：`access.py` 的 `check_access()` 把本地 `credentials.username` 原样 POST 给权限服务，服务端直接据此判定授权，无任何校验。这意味着**任何能访问权限服务的进程都可以声称自己是任意用户**。本地单人使用时风险可控，Agent 场景下则成为必须堵的洞——改由凭据代理签发**签名票据**，权限服务校验签名后才接受其中的身份，而非信任客户端上报值 |
| **越权防护** | 强制校验业务上下文（`businessId` 来自当前环境的 `business.json`，符合 AGENTS.md 约束）；每次调用前经权限服务预检；写操作 HITL |
| **资源控制** | 单次调用超时、输出大小上限、每用户并发与配额限制、进程池复用 |
| **审计闭环** | 会话 ID → LLM 轮次 → 工具调用 → `X-CLI-Invocation-ID` → `CallLog` 可完整回放；新增入口来源便于与客户端预检查分开汇总（现有文档已强调两类检查不应混算） |
| **版本管控** | Agent 镜像内 CLI 版本受控，`X-CLI-Version` 天然满足策略要求，不会出现客户端版本碎片化——这是云侧统一入口的隐性收益 |
| **故障降级** | 权限服务不可用时**必须阻断**受保护请求（与现有网关契约一致），不得降级为放行 |

### 3.6 可观测性

三层追踪，粒度由粗到细：

1. **会话层**：用户、会话 ID、LLM 模型与用量、总耗时。
2. **决策层**：每轮 LLM 的规划、工具选择理由、Token 消耗。
3. **执行层**：工具名、参数（脱敏）、CLI 退出码、耗时、`X-CLI-Invocation-ID`，可关联到权限服务 `CallLog`。

## 4. 演进路线

| 阶段 | 目标 | 主要工作 | 验收标准 |
| --- | --- | --- | --- |
| **P0 只读助手** | 验证价值 | `ml-tool` 网关（L0 命令）＋ 方案 B 凭据 ＋ Web 聊天接入 ＋ CLI 输出契约改造（P0 三项） | 单业务域内，常见查询问题可正确回答，引用真实数据，无越权 |
| **P1 多用户与治理** | 可推广 | 多用户凭据池、KMS 加密、命令分级、HITL 流程、配额、审计报表、`ml schema` | 10–50 用户稳定使用；审计可完整回放；写操作需确认 |
| **P2 平台级集成** | 生产就绪 | 方案 A 身份委托、容器化沙箱、服务层库调用、按业务域拆分多 Agent | 无浏览器依赖；支持写操作；具备容量与故障预案 |

### 建议的第一个里程碑

不要一次做完。建议 P0 只做一件事：**在测试环境、单个业务域内，让 Agent 可靠回答只读查询类问题。**

这一步就能验证三件最有价值的事情：身份方案能否跑通、CLI 输出契约是否够用、平台的授权模型能否覆盖 Agent 场景。

## 5. 风险清单

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 服务端无法完成 SSO 登录（含人机校验） | 阻塞 P0 | Xvfb ＋ 远程浏览器交互式授权；或直接推进方案 A |
| 平台会话有效期仅 1800 秒 | 频繁刷新、影响体验 | Agent 侧后台保活；或平台提供长效凭据 |
| `-o json` stdout 不纯 | 解析失败、回答错误 | 先修 CLI 输出契约（P0 改造项），再做 Agent |
| 平台授权仅绑定账号＋环境 | 越权访问业务数据 | 强制业务上下文校验 ＋ 权限服务预检 ＋ 命令白名单 |
| 浏览器／Python 进程并发成本高 | 资源瓶颈 | 进程池；P2 改为库调用 |
| LLM 误判导致高风险操作 | 生产事故 | L2 强制 HITL，默认拒绝；写操作先 `--dry-run` |
| 权限服务成为单点 | 全站阻断 | 高可用部署；按现有契约明确故障即阻断 |

---

## 6. 与现有组件的关系

| 现有组件 | 本方案如何处理 |
| --- | --- |
| `ml` CLI | **复用**，按 3.3 做最小契约改造；P2 考虑服务层库化 |
| `config.json`／`credentials.json`／`business.json` | 复用其结构；凭据库需从"单机单用户文件"扩展为"按用户隔离的加密存储" |
| 权限服务（`access-service`） | **复用**，作为 Agent 通道的授权与版本准入点；建议新增 `check_source='agent'` |
| `/api/v1/gateway/check` | **复用**其服务端契约（Bearer 密钥、服务端构造身份字段、拒绝必须阻断转发） |
| 版本策略引擎 | **复用**；Agent 镜像统一版本，管控更易生效 |
| `CallLog` | **复用**，扩展入口来源维度 |
| 权限管理台 | **复用**，可新增"Agent 使用"视图 |

**本方案不修改平台后端，不接管业务流量。** 与现有网关文档的边界一致：真正的强制管控仍需实际网关配置完成后才能宣称上线。
