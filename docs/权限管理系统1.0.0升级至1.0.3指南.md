# 权限管理系统 1.0.0 → 1.0.3 升级指南

适用于《权限管理系统Docker安装部署与调试指南.md》中的 Linux x86_64、docker run、离线镜像和外部 MySQL 部署：容器 cli-access，配置目录 /opt/cli-access-config，端口 8008。实际部署修改过的网络、端口和挂载应继续保留。本文是操作指导，不代表生产已执行升级。

## 1. 变化与停机影响

数据库结构由 7 升至 8。新增 cli_version_policies、cli_version_exceptions 两张表，以及 cli_call_logs 的 cli_version、version_source、protocol_version、installation_id、invocation_id、request_id、check_source、version_decision 八个字段；最后更新 schema_versions。

迁移不删除旧表或旧列，不清空人员、管理员、授权、申请、审计和日志，不重置密码。历史日志补充版本 1.0.0、来源 historical_default、协议 1、入口 client；追踪标识为空，版本判断为 NULL。升级后旧客户端未上报版本的新请求按 1.0.0 判断，来源为 legacy_default。

启动不会自动迁移。停机期间依赖权限系统的 CLI 检查可能失败；安排维护窗口，停止全部实例和其他写入来源，不采用新旧版本同时访问同一库的滚动升级。

## 2. 升级前的放行条件

- 核对生产数据库：`SELECT version FROM schema_versions;` 必须只有一条记录，预期为 7。若不是 7，或实际表结构与标记不符，停止并先排查。
- 记录旧镜像 ID、启动参数、网络、端口、挂载、证书；保留旧镜像与旧配置。docker inspect 的完整输出可能含敏感信息，备份文件仅运维可读，不公开分享。
- 完整备份 MySQL 表结构和数据，并在独立测试库实际恢复。备份必须包含权限系统所有表，不仅是 users 和 user_grants。
- 用目标新镜像在恢复出的库演练迁移，迁移配置必须明确指向测试库；验证数据保留、健康检查和授权结果，记录迁移时间与锁等待，以此安排维护窗口。
- 确认迁移账号具备已有读写权限及 CREATE、ALTER、INDEX、REFERENCES 等所需权限。业务数据库密码不写在命令行或发布附件中。
- 保存各表行数、关键 ID 及授权有效期基线，并抽查账号角色、密码哈希、业务关联和历史日志字段。大表全量核验应先评估耗时；仅比较行数不足以证明内容一致。

## 3. 导入镜像（可在停机前完成）

从 v1.0.3 正式 Release 下载镜像、SHA256SUMS、manifest.json 及本指南。不要用 Source code.zip 代替镜像。

```bash
sha256sum --ignore-missing -c SHA256SUMS
docker load -i cli-access-1.0.3-linux-amd64.tar.gz
docker image inspect --format '{{.Id}}' cli-access:1.0.3
docker image inspect --format '{{index .Config.Labels "org.opencontainers.image.revision"}}' cli-access:1.0.3
```

确认镜像文件出现在校验输出中并显示 OK；配置 ID、源码提交分别与 manifest.json 的 image_id、image_revision 一致。文件 SHA256、镜像配置 ID 和仓库摘要不是同一个值，不能互相比较。任一步失败都不要继续。

## 4. 停写与最终备份

进入维护窗口，暂停业务请求及管理台变更，并停止全部旧实例。标准单实例部署执行：

```bash
docker stop --time 30 cli-access
```

**现在完成最终数据库备份和配置目录备份，记录数据基线，再进入下一节。** 不以几小时前的在线备份代替最终恢复点。备份方式由数据库运维按实际 MySQL、存储引擎和备份工具确认；记录恢复命令、所需凭据及恢复耗时。保留原 service.env，不复制示例覆盖。

## 5. 显式迁移（只有一个进程）

挂载与原应用相同的配置目录；DATABASE_URL 必须核实为本次目标生产数据库：

```bash
docker run --rm \
  -v /opt/cli-access-config:/run/cli-access:ro \
  cli-access:1.0.3 python -m app.manage migrate
```

若旧部署使用自定义 Docker 网络，也为迁移容器加入同样的 --network 参数。命令必须成功退出，预期输出“数据库初始化完成（版本 8）”；这里对旧库执行的是增量升级。

检查 schema_versions 恰有一行且为 8、新表和八个字段齐全，核对迁移前后原有数据。不要仅凭版本数字判断全部正确。

失败时保持应用停止。MySQL DDL 可能已提交部分修改，不能假设整个迁移已自动回滚。程序逐表逐列检查，允许排除故障后重跑，但仍需先检查现场；不要并发迁移、手删业务表或手改版本号跳过迁移。

## 6. 替换容器

仅当上一节成功后执行。保留已停止的旧容器，若该备份名称已存在，先确认归属并使用唯一名称：

```bash
docker rename cli-access cli-access-1.0.0-backup

docker run -d \
  --name cli-access \
  --restart unless-stopped \
  -v /opt/cli-access-config:/run/cli-access:ro \
  -p 8008:8008 \
  --read-only \
  --tmpfs /tmp:size=64m,mode=1777 \
  --cap-drop ALL \
  --security-opt no-new-privileges:true \
  --log-driver local \
  --log-opt max-size=10m \
  --log-opt max-file=5 \
  cli-access:1.0.3
```

端口、网络、证书挂载应以原部署为准；上述端口绑定所有网卡，保留已有内网访问限制。旧容器保持停止，不启动到已经迁移的库。不要运行 create-admin，也不要重建数据库。仅 docker restart 不能更换容器镜像。

## 7. 验收后恢复访问

保持业务入口关闭，运维执行受控验收：

```bash
docker logs --tail=200 cli-access
docker inspect --format '{{.State.Health.Status}}' cli-access
curl --fail --max-time 5 http://127.0.0.1:8008/cli-permission/healthz
```

预期 healthy，健康接口 HTTP 200 且内容为 {"status":"ok"}。还必须验证：

- 原管理员登录正常；人员、环境、授权状态、有效期及历史记录正确。
- 有效授权通过，未授权、停用或过期授权拒绝；使用专用验收账号和无副作用命令。
- 新日志可写；旧客户端无版本标识时记录 1.0.0，新客户端记录真实上报版本。
- 版本管理页面可访问；默认迁移不会创建任何强制版本策略。
- 新服务重启后健康，错误日志和数据库负载无异常。

全部通过后恢复业务访问并观察。版本强制限制另行分阶段上线：先观察实际版本分布，再提醒升级，最后按明确范围强制拒绝。服务升级不等于所有业务 CLI 必须立即升级。

## 8. 回滚

- 迁移尚未开始：旧库未变更，可以重新启动旧容器。
- 迁移开始后（含中途失败）：检查结构变动，不默认允许直接启动旧版。
- 已迁移到 8：1.0.0 的健康检查要求 7，不能只切换镜像；没有自动降级迁移。

推荐停新服务、保留故障库，将最终备份恢复到独立回滚库；使用旧镜像、原部署参数和指向回滚库的独立配置目录重新启动，验证后恢复访问。核实所有恢复配置均指向回滚库，避免旧容器仍使用指向结构 8 的原配置。

新服务恢复业务写入后，回滚旧备份会缺失备份后的新增数据；必须先保存并制定增量处理方案，不能直接覆盖唯一数据副本。禁止将 schema_versions 手改成 7 冒充回滚。保留旧镜像、备份和日志直到观察期结束，再按运维保留策略清理。
