# CLI 版本管控与网关接入

适用客户端：`wiserec-cli 1.0.3`；权限服务数据库结构版本：`8`。

## 管控规则

- 请求缺少 `X-CLI-Version` 时，以 **1.0.0** 参与判断，来源记为“旧客户端默认”。是否携带客户端名称不影响此规则。
- 已携带但为空、重复或格式不合法的版本不会回退到 1.0.0。正式版本必须为三段数字，每段最多 9 位，不含前导零、预发布或构建后缀。
- 按数字比较版本，例如 1.0.10 大于 1.0.9。高于最低要求的未知正式版本默认允许。
- 全局、环境、环境＋业务策略可以叠加。所有适用的强制最低版本取最高值；任一强制策略禁用该版本即拒绝。
- 仅观察：记录判断，不提醒、不拒绝。提醒升级：记录并提醒，不拒绝。强制拒绝：执行最低版本、禁用版本、格式及协议约束。
- 协议版本当前为 `1`；缺失时按 `1`，不受支持的协议在强制策略下拒绝。
- 未配置适用的强制策略时，不新增版本准入限制，原有账号、环境授权继续执行。
- 临时例外指定策略、账号、环境、业务、版本闭区间和未来失效时间，只豁免该策略的最低版本；无法绕过禁用版本、协议检查、其他策略或账号授权。
- 策略时间由服务端判断。界面时间为北京时间，数据库存储 UTC。

## 管理操作

登录权限管理台，进入“CLI 版本管理”。管理员可查看，超级管理员可发布、停用、重新启用策略及批准或撤销例外。所有变更要求有效会话和 CSRF，写入操作审计。

1. 新增策略，先选择“仅观察”，配置范围、最低/推荐版本、禁用版本和升级说明地址。
2. 预览最近 7 天历史检查，在策略生效时刻的组合规则下预计会拒绝多少次检查。预览包含原有策略，不是新增拒绝数量，也不代表用户或设备数量。
3. 确认发布。逐步改为提醒或强制：新增相应策略并停用原策略；保留历史策略以便回滚。
4. 临时升级困难可批准有期限的例外。审批人即当前超级管理员，原因写入审计。
5. 回滚新策略时停用它，必要时重新启用旧策略。先确认仍适用的其他强制策略，避免误以为停用一条即可降低全部门槛。

当前不缓存策略，每次检查读取数据库。无需等待客户端重新安装即可更新限制；已经通过检查并开始执行的操作不会被追溯撤销。例外到期后下一次检查自动生效。

## 使用分布和日志

- 版本管理按环境、业务、版本、版本来源和检查入口汇总，默认最近 7 天，可选 1、7、30、90 天；展示检查次数、版本拒绝次数、账号数和最近使用时间，支持环境与业务筛选。
- 调用日志支持按业务 ID、CLI 版本筛选，显示版本来源、命中策略、例外、安装实例和命令关联信息。
- 一次命令可产生多次检查。客户端预检查和网关检查分开汇总，均不等于业务执行成功或设备数量。
- 历史日志迁移后采用 1.0.0，标记“历史默认推定”；这不是已验证的历史运行版本。
- 安装但未发出请求的客户端无法统计。版本与安装 ID 均为客户端声明，不用于认证。

## CLI 行为

1.0.3 在权限预检查、平台业务请求、Jupyter HTTP 和 WebSocket 握手携带：

| 请求头 | 内容 |
| --- | --- |
| `businessid` | 当前环境 business.json 的 selected.businessId |
| `X-CLI-Name` | wiserec-cli |
| `X-CLI-Version` | 当前运行包的内置版本 |
| `X-CLI-Protocol-Version` | 1 |
| `X-CLI-Installation-ID` | 用户配置目录 installation-id 中持久保存的随机 UUID |
| `X-CLI-Invocation-ID` | 每次 CLI 命令的关联 UUID |
| `X-Request-ID` | 请求 UUID；平台调用显式传入的关联值保留 |

`ML_CLIENT_STATE_DIR` 可为测试或受限部署指定 installation-id 的目录；它不修改业务配置路径或版本。目录不可写或标识文件损坏时省略安装 ID，不影响版本检查。不要将该 ID 当作可靠的机器标识。

版本拒绝提示当前版本、最低要求、推荐版本及升级说明，返回非零退出码；不触发重新登录或自动重试。提醒每次命令最多输出一次，写入 stderr，不污染 JSON stdout。帮助、`ml --version` 等本地操作不受版本策略限制。

命令未增加。可使用已有 `ml access status` 验证当前账号、业务和环境；`ml access status --diagnose` 可显示当前运行版本和权限请求诊断。

## 服务端接口

### 客户端预检查（兼容旧客户端）

`POST /cli-permission/api/v1/access/check`

保持现有 JSON 请求结构和 HTTP 200 的 allowed 判定。版本信息通过请求头传递。允许时可追加 version_policy；拒绝时返回 allowed=false、reason/code 和版本要求。旧版 CLI 不理解新的原因时会显示通用拒绝提示，但仍停止业务操作。

### 可信网关检查

`POST /cli-permission/api/v1/gateway/check`

新增环境变量 `CLI_GATEWAY_TOKEN`，至少 32 字符，由服务端安全生成，只配置在权限服务和网关。不得打包进 CLI、提交仓库、放进网页或转发到业务客户端。未配置或长度不足时接口返回 503；认证失败返回 401。

网关请求必须携带 `Authorization: Bearer <服务端密钥>` 和 `businessid`；传递客户端版本头（缺失时保持缺失，权限服务按 1.0.0）。JSON 示例：

```json
{
  "username": "alice",
  "environment": "prod",
  "platform_origin": "https://platform.example.com",
  "command": "ml train list"
}
```

**接入契约：** username 必须来自网关完成认证后的身份；businessid 必须经过该身份的业务访问权限校验；environment、platform_origin 必须来自网关的服务端路由配置，不得直接采信客户端 JSON。权限服务现有授权仅绑定账号与环境，不替代平台业务权限。

成功返回 HTTP 200 且 allowed=true 才可继续转发；拒绝返回 HTTP 403，例如：

```json
{
  "allowed": false,
  "reason": "CLI_VERSION_TOO_OLD",
  "code": "CLI_VERSION_TOO_OLD",
  "current_version": "1.0.0",
  "version_source": "legacy_default",
  "minimum_version": "1.0.3",
  "recommended_version": "1.0.3",
  "request_id": "由请求携带的追踪标识"
}
```

请求/响应还有其他字段，示例并非完整结构。业务网关应透传拒绝 JSON，客户端才能区分版本拒绝与认证失效。异常、超时、非 200 或 allowed 不为布尔 true 均不得转发业务请求。建议不缓存允许结果，以保持停用、例外到期和新策略立即生效；服务故障会阻断受保护请求，需配套高可用部署。

权限服务响应的 policy_revision 是命中策略中最大策略 ID，仅用于辅助定位；**不是缓存版本或 ETag**。判断和审计以完整 policy_ids/checks、规则记录与操作审计为准。

## 强制管控部署边界

本仓库包含 CLI 和权限服务，不包含实际业务网关、平台身份发行端或后端网络配置。新增网关接口是集成点，不会自动接管业务流量。

必须由实际网关完成以下配置后，才能宣称服务端强制管控已上线：

1. 在指定的 CLI 访问通道执行认证和业务归属校验，再调用可信网关检查接口。
2. 对该通道的所有请求执行检查，不能仅在存在 X-CLI-Name 或 X-CLI-Version 时检查；缺失版本按 1.0.0。
3. 在调用实际业务服务前拒绝，不得先执行后检查；禁止绕过网关直接访问后端。
4. 网页与 CLI 共用 Cookie/API 时，必须明确通道边界。不能仅依靠客户端名称、User-Agent 或可删除的请求头区分网页与 CLI。需要独立凭据或由平台认定的访问路径，同时关闭旧凭据的旁路。
5. Jupyter HTTP 与 WebSocket 握手都要接入。已建立的长连接不会自动重查；普通升级允许会话结束，紧急中止已有会话由实际网关或 Jupyter 管理端负责。
6. 向客户端提供升级文档和安装包入口，避免低版本被拒绝后无法获得升级资源。

版本上报、网关密钥乃至服务端签发的访问令牌都不能证明用户没有修改 CLI 或伪造版本。若需要校验真实二进制，须另行使用受控终端/可信执行方案。

## 升级和回滚步骤

1. 备份 MySQL，停止旧权限服务；先执行 `bash manage.sh migrate`，结构升级为 8（可重入，兼容旧日志）。
2. 部署新版权限服务，健康检查通过后先保留无强制策略状态。旧客户端请求仍可按既有授权运行，其版本记作 1.0.0。
3. 发布 1.0.3 CLI，并核对包元数据与 `ml --version` 一致。旧安装方式继续使用，升级包地址由实际发布渠道提供。
4. 配置观察和提醒策略，确认影响范围，再启用强制限制；按上述契约接入网关。
5. 先在测试环境验收缺失版本、低版本、切换环境/业务、例外到期、网关错误、直接访问旁路和 WebSocket。
6. 应急首先停用有问题的策略。数据库结构不提供降级迁移；如需回退旧服务，请恢复升级前数据库备份并配合维护窗口，勿让旧服务和新版 schema 混跑。

仓库自动化覆盖 SQLite 上的迁移与权限/策略回归；生产 MySQL DDL、真实网关和平台认证链路仍需部署环境验收。
