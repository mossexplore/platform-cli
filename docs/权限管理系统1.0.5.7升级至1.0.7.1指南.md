# 权限管理系统 1.0.5.7 → 1.0.7.1 升级指南

适用于 Linux x86_64、外部 MySQL 8.x、`docker run` 部署；示例容器名为 `cli-access`，配置目录为 `/opt/cli-access-config`。实际网络、端口、挂载、代理和 TLS 参数应沿用现有部署。本指南不代表生产升级已经执行。CLI 也升级至 1.0.7.1，Windows 安装器同版本重装时仍会替换包内 Wheel，重装和升级保留已选环境及自动保活设置。

## 1. 核对现状与结构

- 上一正式版本：`cli-access:1.0.5.7`，数据库结构 **10**。
- 目标版本：`cli-access:1.0.7.1`，数据库结构 **11**。
- 已逐文件比较两个版本的 `access-service/app/migrations.py` 和相关模型：新增 `environments.default_grant BOOLEAN NOT NULL DEFAULT 0`，已有环境的“默认开通”标识统一关闭。人员、管理员、环境、授权和申请记录保留；该标识只控制审批预选，不会自动审批或修改已有授权。本次必须先显式迁移结构，再启动新服务，不重新运行 `create-admin`。新库仍按部署指南初始化。

在现有数据库查询 `SELECT version FROM schema_versions;`，确认恰有一行且为 10，并核对管理员、人员、授权、日志、申请和策略。若结构不是 10，停止升级，按真实结构及历史指南制定迁移方案；不得手改 `schema_versions`。目标服务健康检查要求结构 11，未迁移不能直接启动。

## 2. 演练、下载与校验

记录当前容器、镜像 ID/摘要、配置目录、网络、端口、数据库连接目标及各表行数。先备份数据库与配置，在**独立测试库**完成恢复演练，再以目标镜像对该测试库显式迁移，核对健康、管理员登录、授权允许/拒绝、日志和有数据的数据看板。演练不得连接生产库。原 `service.env` 及外部 MySQL 保留，不使用附件示例覆盖真实配置。

从 [v1.0.7.1 正式 Release](https://github.com/mossexplore/platform-cli/releases/tag/v1.0.7.1) 下载镜像、`SHA256SUMS`、`manifest.json` 和本指南。核对已下载文件哈希后导入：

```bash
sha256sum --ignore-missing -c SHA256SUMS
docker load -i cli-access-1.0.7.1-linux-amd64.tar.gz
docker image inspect --format '{{.Id}}' cli-access:1.0.7.1
docker image inspect --format '{{index .Config.Labels "org.opencontainers.image.revision"}}' cli-access:1.0.7.1
```

镜像配置 ID、版本和源码提交须与 manifest 一致；文件 SHA256、Docker image ID 和仓库镜像摘要是不同对象。任一校验不符应停止。

## 3. 维护窗口与最终备份

暂停管理台变更和权限检查入口，停止全部 1.0.5.7 实例及其他写入来源。单实例示例：

```bash
docker stop --time 30 cli-access
```

**停止写入后，现在完成最终数据库备份和配置目录备份。** 核对备份文件可读、恢复位置明确，并记录管理员、授权、日志、审计、申请及策略的数量和关键值。确认最终备份可用后才继续迁移。备份失败必须停止升级，不要删除旧容器或镜像。

## 4. 迁移并切换至 1.0.7.1

### 4.1 显式迁移数据库

确认全部写入仍已停止、最终备份已完成、数据库仍为结构 10，再使用目标镜像和原配置目录，由**一个进程**执行迁移：

```bash
docker run --rm -v /opt/cli-access-config:/run/cli-access:ro \
  cli-access:1.0.7.1 python -m app.manage migrate
```

迁移进程沿用实际网络及 TLS 参数；若 MySQL 通过自定义 Docker 网络访问，应使用与原服务相同的网络。不要同时运行多个迁移进程或启动新旧服务写库。MySQL DDL 可能自动提交；列已添加但结构版本未更新时，迁移会检查列是否存在，可在确认备份与状态后重跑。迁移失败时保持停机排查，不能跳过迁移或手改结构版本。

查询 `SELECT version FROM schema_versions;`，确认恰有一行且为 **11**；核对新列存在，原环境的 `default_grant` 均为 `0`，人员、管理员、授权、申请、日志和策略与最终备份基线一致。数据核对不通过时不得启动放行。

### 4.2 切换容器

保留已停止的旧容器，给它一个未使用的备份名称：

```bash
docker rename cli-access cli-access-1.0.5.7-backup
```

沿用实际网络、端口和挂载配置；以下仅为单实例示例，启动参数与上一正式版升级指南保持一致：

```bash
docker run -d \
  --name cli-access \
  --restart unless-stopped \
  -v /opt/cli-access-config:/run/cli-access:ro \
  -p 8008:8008 \
  --read-only \
  --tmpfs /tmp:size=64m,mode=1777 \
  --cap-drop ALL \
  --security-opt no-new-privileges:true \
  --log-driver local \
  --log-opt max-size=10m \
  --log-opt max-file=5 \
  cli-access:1.0.7.1
```

端口示例绑定所有网卡，生产应保留现有网络限制与 TLS/Nginx 设置。原管理员账号和配置继续使用，不创建新管理员。

## 5. 验收与放行

保持业务入口关闭，核查容器健康、日志和数据库结构：

```bash
docker inspect --format '{{.State.Health.Status}}' cli-access
docker logs --tail=200 cli-access
curl --fail --max-time 5 http://127.0.0.1:8008/cli-permission/healthz
```

确认结构为 **11**；管理员登录、人员与授权、历史日志、申请和策略与备份基线相符。执行一次授权允许和拒绝检查，确认新日志落库；打开**有数据**的数据看板，确认页面正常、图表 JSON 可解析且计数为数字。核对人员授权页环境标签展开、收起及长名称换行正常，环境别名和时间列完整显示。

在环境管理中按需要设置“默认开通”标识，确认审批只预选已启用且带标识的环境，无默认环境时不预选，快捷按钮正常；预览后配置变化会要求重新核对。用新版 CLI 核对登录后的申请提示、环境别名，以及重装、升级后所选环境保持不变。重启容器并确认挂载配置生效。验收通过后再恢复业务入口并观察错误日志。

## 6. 回滚

本次涉及结构 **10 → 11**，没有结构 11 → 10 的降级迁移。若新镜像验收失败，先停止 1.0.7.1 容器并保持入口关闭。旧版健康检查要求结构 10，**不能只切回 1.0.5.7 镜像连接结构 11 数据库**，也不能手改 `schema_versions` 冒充回滚。

保留故障库供取证，把停写后的结构 10 最终备份恢复到**独立回滚库**，核对原配置确实指向该库，再用保留的 1.0.5.7 镜像和原网络、端口、挂载参数启动。核对健康、管理员登录、人员、授权、原有版本策略及日志后放行。旧容器名若已被占用，先核对并调整名称；不要同时运行新旧应用写入同一库。

恢复备份会丢失备份后新增的默认配置、申请审批、授权变更、日志和审计；若已经放行写入，须先保存并明确损失范围及补录方案，再决定回滚。保留旧镜像、最终备份和日志直到观察期结束。
