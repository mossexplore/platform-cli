# cli-access 1.1.2 与知识库网关 0.1.0 联合升级指南

适用于 Linux x86_64、外部 MySQL 8、现有 `cli-access` 容器和内网 WeKnora Wiki。按 **核对生产基线 → 离线演练 → 停写备份 → 切换权限服务 → 启用网关 → 双账号验收** 执行。目标是部署支持 `ml kb` 的签票服务和只读网关。客户端另行分发启用知识库的 Go CLI。

## 1. 核对现状与数据库结构

| 当前部署 | 本次操作 |
| --- | --- |
| `cli-access` 1.1.1，结构 15 | 切换到 `cli-access:1.1.2-85b109761c01`。这两个版本的迁移代码和数据库模型一致，无需迁移。 |
| 已部署上一构建 `cli-access:1.1.2-17d0e9fc3315`，结构 15 | 按同样步骤更换镜像，以镜像 ID 和 revision 区分两次构建。保留原有签票密钥。 |
| 数据库结构早于 15 | 先按实际结构完成相应迁移、备份和验收，再进入本指南。结构 13 的路径见[结构 13 升级至 1.1.1 指南](权限管理系统结构13升级至1.1.1指南.md)。 |
| 首次部署网关／已有网关 | 首次部署创建网关配置和日志卷；已有网关先记录原镜像 ID、容器名、配置、网络及卷。如果已是本指南的镜像 ID 且配置相符，可直接做联调验收。 |

在生产权限库执行只读查询 `SELECT version FROM schema_versions;`，确认只有一行且值为 15。核对现有管理员、人员、授权、调用日志和版本策略。记录两服务所在主机、原镜像 ID、网络、端口、反代、配置及日志挂载位置，确认备份容器名可用。

```bash
docker inspect --format '{{.Name}} {{.Config.Image}} {{.Image}}' cli-access
docker ps -a --filter name=wiserec-kb-gateway
```

## 3. 维护窗口与最终备份

暂停权限管理台变更、准入流量及其他写入来源。已有网关也先暂停其外部入口。保留受控验收通道。停止所有旧权限服务实例，单实例命令如下。

```bash
docker stop --time 30 cli-access
```

**此时完成最终备份，再进入切换。** 由 DBA 按已演练的方式备份外部 MySQL，记录备份时间、恢复位置及关键表数量。备份 `/opt/cli-access-config` 全目录（含真实 `service.env`）、既有网关 env、反代配置，并保留原镜像、容器和审计卷。验证备份可读、恢复人员可取用。密钥和数据库凭据按生产秘密配置保管。

## 4. 切换服务与配置

### 4.1 在权限服务添加知识库签票 AK 和 SK

从 v1.1.1 首次启用 `ml kb` 时，在**权限服务宿主机**编辑现有的 `/opt/cli-access-config/service.env`。下方启动命令将它挂载到容器内的 `/run/cli-access/service.env`。若现网使用其他挂载目录，请编辑对应的宿主机文件。保留原有数据库、管理员及 TLS 配置。

1. 为这次部署选一个 AK，例如 `kb-prod-v1`。它是密钥标识，可用 1 至 64 个英文字母、数字、下划线或短横线。
2. 在受控终端执行 `openssl rand -hex 32` 生成 SK，将输出的 64 个十六进制字符作为完整密钥文本保存到生产密钥管理工具。权限服务和网关使用同一串文本。已有有效 AK/SK 的部署沿用原值。
3. 在现有 `service.env` 中添加以下两行。已有同名空项时就地填写，每个字段只保留一行。将尖括号占位符连同括号一起替换为真实值。

   ```dotenv
   KB_TICKET_AK=kb-prod-v1
   KB_TICKET_SK=<上一步生成的完整SK>
   ```

4. 通过受控渠道将同一对值交给网关部署人员，在第 4.3 节的 `kb-gateway.env` 中填写 `KB_TICKET_KEYS=kb-prod-v1:<同一完整SK>`。若自定义了 AK，也同步替换冒号左侧的标识。WeKnora 提供的 Scoped API Key 单独填入 `WEKNORA_API_KEY`。客户端无需分发这些密钥。

### 4.2 启动新版权限服务

权限服务启动时读取挂载文件。首次切换按下列步骤启动 1.1.2；若 1.1.2 已运行且刚补填挂载文件，执行 `docker restart cli-access` 后直接做健康检查。确认仍为结构 15 后，首次切换使用已核对为空闲的备份名保留旧容器。

```bash
docker rename cli-access cli-access-before-1.1.2-backup
```

以下为基准部署命令。实际端口绑定、网络和 TLS 沿用现网配置。

```bash
docker run -d \
  --name cli-access \
  --restart unless-stopped \
  -v /opt/cli-access-config:/run/cli-access:ro \
  -p 8008:8008 \
  --read-only \
  --tmpfs /tmp:size=64m,mode=1777 \
  --cap-drop ALL \
  --security-opt no-new-privileges:true \
  --log-driver local \
  --log-opt max-size=10m \
  --log-opt max-file=5 \
  cli-access:1.1.2-85b109761c01
```

检查权限服务健康、日志及反代入口。以下为本机 HTTP 示例，现网启用 TLS 时沿用实际协议和证书。

```bash
docker inspect --format '{{.State.Health.Status}}' cli-access
docker logs --tail=200 cli-access
curl --fail --max-time 5 http://127.0.0.1:8008/cli-permission/healthz
```

### 4.3 启用知识库网关

在 WeKnora 为已启用 Wiki 的目标库发布一篇验收页面，签发限库且仅具 `retrieve` 权限的 Scoped API Key。首次部署时准备目录和模板，已有配置直接编辑受控副本。

```bash
# 创建网关目录。所有者可读写和进入，同组用户可查看和进入，其他用户无权访问。
install -d -m 0750 /opt/wiserec-kb-gateway

# 创建日志目录，并将所有者和组设为容器使用的 65532，让网关能写入审计日志。
install -d -o 65532 -g 65532 -m 0750 /opt/wiserec-kb-gateway/logs

# 如果正式配置文件不存在，就复制一份模板，仅允许所有者读写。已有配置会保留。
test -e /opt/wiserec-kb-gateway/kb-gateway.env || install -m 0600 /opt/offline/kb-0.1.0/kb-gateway.env.example /opt/wiserec-kb-gateway/kb-gateway.env
```

| 网关 env 字段 | 生产取值 |
| --- | --- |
| `WEKNORA_BASE_URL`、`WEKNORA_API_KEY` | 容器内可达的 WeKnora 后端地址和上一步的 Scoped Key。确认 `weknora-net` 存在且后端已接入。 |
| `KB_TICKET_KEYS` | 设为权限服务的同一对 `AK:SK`。此密钥与 WeKnora API Key 分别管理。 |
| `WEKNORA_ALLOWED_KB_IDS` | 正式开放的库 ID，多个用逗号分隔。 |
| `WEKNORA_PREVIEW_KB_IDS`、`KB_PREVIEW_USERS` | 可选灰度库 ID 和精确匹配的 `环境:账号`。正式与灰度库 ID 分开配置，灰度仅用于非涉密资料。 |
| `KB_GATEWAY_ALLOWED_CIDRS`、`KB_GATEWAY_TRUSTED_PROXY_CIDRS` | 前者按容器实际看到的 TCP 对端放行。若需按员工 IP 限流，仅将会强制覆写 `X-Real-IP` 的可信反代地址段填入后者。Docker 端口转发后的对端地址需在演练中确认。 |

跨主机部署时，将反代上游指向网关宿主机的内网 IP 和 8087 端口，并在安全组或防火墙中将该端口的入站来源限定为反代。将网关实际看到的反代来源加入 `KB_GATEWAY_ALLOWED_CIDRS`。修改 Docker 端口映射需要重新创建容器。

已有同名网关且需要替换时，先停止并保留为 `wiserec-kb-gateway-before-upgrade`。首次部署跳过这一步。使用部署指南的同一条命令创建容器：

```bash
docker run -d \
  --name wiserec-kb-gateway \
  --network weknora-net \
  --restart unless-stopped \
  --read-only \
  --cap-drop ALL \
  --security-opt no-new-privileges:true \
  --security-opt seccomp=unconfined \
  --env-file /opt/wiserec-kb-gateway/kb-gateway.env \
  -v /opt/wiserec-kb-gateway/logs:/var/log/kb-gateway \
  -p 8087:8087 \
  --log-driver json-file \
  --log-opt max-size=10m \
  --log-opt max-file=3 \
  wiserec-kb-gateway:0.1.0
```

若已有网关且修改了 `--env-file`，需按上面的步骤重新创建网关容器才会载入新值。第 5 节的 `ml kb list` 可验证实际签票和验签是否成功。

上述命令沿用旧版 Docker 兼容参数。使用现有 HTTPS 反代接入网关，对外提供 CLI 打包时锁定的地址。验收终端需使用启用 KB 的 `ml.exe`，其 CA 配置应同时信任权限服务和网关。完整反代和打包设置见[网关配置部署与使用指南](../deployment/kb-gateway配置部署与使用指南.md)。

## 5. 验收与放行

### 5.1 在网关宿主机检查进程

按第 4.3 节的默认端口执行。预期返回 HTTP 200 和 `{"status":"ok"}`。该接口只检查网关进程，业务读取在第 5.3 节验证。

```bash
curl --noproxy '*' -iS --max-time 5 http://127.0.0.1:8087/health
```

如果不通，依次查看容器是否运行、宿主机端口是否映射、启动日志是否有配置错误。

```bash
docker ps -a --filter name=wiserec-kb-gateway
docker port wiserec-kb-gateway
docker logs --tail 100 wiserec-kb-gateway
```

### 5.2 从员工终端验证 HTTPS 入口和验票

通过受控验收通道访问 CLI 实际使用的网关地址。将下面的示例域名替换为现场地址，保留证书校验。两个请求都无需提供票据或 API Key。

```bash
gateway_url='https://kb-gateway.internal.example.com'
curl -iS --max-time 10 "$gateway_url/health"
curl -iS --max-time 10 "$gateway_url/v1/kb/list"
```

| 请求 | 预期结果 | 异常时检查 |
| --- | --- | --- |
| `GET /health` | HTTP 200，`{"status":"ok"}` | 若宿主机检查成功，排查员工终端的域名解析、证书信任及反代路由。 |
| 无票据的 `GET /v1/kb/list` | HTTP 401，`{"code":"INVALID_TICKET"}`，说明请求已到达网关验票环节。 | 若返回 `403 SOURCE_DENIED`，核对 `KB_GATEWAY_ALLOWED_CIDRS` 是否允许网关实际看到的反代来源 IP。 |

### 5.3 验证授权、知识库读取和审计

1. **原有权限能力。** 保持外部流量暂停，登录原管理员账号，核对授权、策略和历史日志。做一次普通命令准入允许及拒绝检查，确认日志落库。有数据的数据看板应正常打开，图表 JSON 可解析且统计值为数值。
2. **双账号验收。** 在各自终端或 DSH 会话中绑定受支持环境、登录、选中业务。使用启用知识库功能的 CLI。先从库列表复制实际库 ID，再从页面目录复制已发布页面的 slug，用该页面中已有的词测试搜索。

   ```shell
   ml kb list
   ml kb page list --kb KB_ID
   ml kb search "验收关键词" --kb KB_ID
   ml kb page show PAGE_SLUG --kb KB_ID
   ```

   普通账号应能列出预期正式库、读取已发布页正文，并用验收关键词搜到该页。这三项成功说明权限服务签票、网关验票和 WeKnora 读取均已打通。若已登录的 CLI 返回网关错误 `401 INVALID_TICKET`，核对两端签票 AK/SK 和宿主机时钟。若库列表为空，核对正式库白名单、WeKnora API Key 的授权范围以及目标库是否启用 Wiki。启用灰度时，普通账号指定灰度 ID 应返回 `404 KB_NOT_FOUND`，名单内调试账号在对应环境应能读取同一已发布页。涉及草稿的检查应确认正文未返回。
3. **审计与持久性。** 从权限管理台调用详情取得成功查询的票据 ID，在网关当日 `/opt/wiserec-kb-gateway/logs/kb-audit-YYYY-MM-DD.jsonl` 中核对相同 `ticket_id`、账号、动作和状态。重启新容器后复查健康、查询和日志持久化。上述项目通过后放行，并观察 401、403、429、502 和审计写入错误。

## 6. 回滚

**只有 KB 查询失败时**，先关闭 KB 对外入口，保留网关日志。权限服务原有授权功能验收通过即可继续对外服务。首次引入网关时停止新网关即完成该侧撤回；替换既有网关时，停用并改名保留新容器，再将原容器恢复原名并启动，复查原网关路由、票据密钥和日志卷。

**权限管理或原有准入也异常时**，暂停写入及两个入口，按以下顺序恢复旧权限服务。先确认下列故障容器名空闲。

```bash
docker stop --time 30 cli-access
docker rename cli-access cli-access-1.1.2-failed
```

从第 3 节的配置备份恢复原挂载目录、权限和 TLS 设置，确认连接目标是原结构 15 数据库，再执行：

```bash
docker rename cli-access-before-1.1.2-backup cli-access
docker start cli-access
docker inspect --format '{{.State.Health.Status}}' cli-access
docker logs --tail=200 cli-access
curl --fail --max-time 5 http://127.0.0.1:8008/cli-permission/healthz
```

本路径没有结构变更，可直接回滚应用镜像，无需降级迁移。回到 1.1.1 后应保持 KB 入口关闭，旧权限服务不能签发新票据。复查管理员登录、普通命令准入及审计后恢复原业务流量。若数据库内容受损，先保留故障库，将最终备份恢复到独立回滚库并核对配置；使用备份会失去备份后的新增记录，先保存增量并制定补录方案。禁止手改 `schema_versions`。保留旧容器、镜像、备份及日志至观察期结束。
