# 权限管理系统 1.0.3.1 → 1.0.3.2 升级指南

适用于 Linux x86_64、外部 MySQL 8.x、`docker run` 部署；示例容器名为 `cli-access`，配置目录为 `/opt/cli-access-config`。实际网络、端口、挂载、代理和 TLS 参数应沿用现有部署。本指南不代表生产升级已经执行。CLI 也升级至 1.0.3.2，Windows 安装器同版本重装时仍会替换包内 Wheel。

## 1. 核对现状与结构

- 上一正式版本：`cli-access:1.0.3.1`，数据库结构 **10**。
- 目标版本：`cli-access:1.0.3.2`，数据库结构 **10**。
- 已逐文件比较两个版本的 `access-service/app/migrations.py` 和相关模型：没有数据库结构变化；本次服务改动是数据看板聚合计数处理和调用日志布局。已有结构 10 且管理员、数据正常时无需执行 `migrate`，也不要重新运行 `create-admin`。新库仍按部署指南初始化。

在现有数据库查询 `SELECT version FROM schema_versions;`，确认恰有一行且为 10，并核对管理员、人员、授权、日志和策略。若结构不是 10，停止升级，按真实结构及历史指南制定迁移方案；不得手改 `schema_versions`。

## 2. 演练、下载与校验

记录当前容器、镜像 ID/摘要、配置目录、网络、端口、数据库连接目标及各表行数。先备份数据库与配置，在**独立测试库**完成恢复演练，并以目标镜像连接该测试库核对健康、管理员登录、授权允许/拒绝、日志和有数据的数据看板。原 `service.env` 及外部 MySQL 保留，不使用附件示例覆盖真实配置。

从 [v1.0.3.2 正式 Release](https://github.com/mossexplore/platform-cli/releases/tag/v1.0.3.2) 下载镜像、`SHA256SUMS`、`manifest.json` 和本指南。核对已下载文件哈希后导入：

```bash
sha256sum --ignore-missing -c SHA256SUMS
docker load -i cli-access-1.0.3.2-linux-amd64.tar.gz
docker image inspect --format '{{.Id}}' cli-access:1.0.3.2
docker image inspect --format '{{index .Config.Labels "org.opencontainers.image.revision"}}' cli-access:1.0.3.2
```

镜像配置 ID、版本和源码提交须与 manifest 一致；文件 SHA256、Docker image ID 和仓库镜像摘要是不同对象。任一校验不符应停止。

## 3. 维护窗口与最终备份

暂停管理台变更和权限检查入口，停止全部 1.0.3.1 实例及其他写入来源。单实例示例：

```bash
docker stop --time 30 cli-access
```

**停止写入后，现在完成最终数据库备份和配置目录备份。** 核对备份文件可读、恢复位置明确，并记录管理员、授权、日志、审计及策略的数量和关键值。确认最终备份可用后才继续。不要删除旧容器或镜像。

## 4. 切换至 1.0.3.2

确认数据库仍为结构 10。此升级**不运行迁移命令**；若检查发现结构或数据异常，保持停机排查。保留已停止的旧容器，给它一个未使用的备份名称：

```bash
docker rename cli-access cli-access-1.0.3.1-backup
```

沿用实际网络、端口和挂载配置；以下仅为单实例示例：

```bash
docker run -d \
  --name cli-access \
  --restart unless-stopped \
  -v /opt/cli-access-config:/run/cli-access:ro \
  -p 8008:8008 \
  --read-only \
  --tmpfs /tmp:size=64m,mode=1777 \
  --cap-drop ALL \
  --security-opt no-new-privileges:true \
  --log-driver local \
  --log-opt max-size=10m \
  --log-opt max-file=5 \
  cli-access:1.0.3.2
```

端口示例绑定所有网卡，生产应保留现有网络限制与 TLS/Nginx 设置。原管理员账号和配置继续使用，不创建新管理员。

## 5. 验收与放行

保持业务入口关闭，核查容器健康、日志和数据库结构：

```bash
docker inspect --format '{{.State.Health.Status}}' cli-access
docker logs --tail=200 cli-access
curl --fail --max-time 5 http://127.0.0.1:8008/cli-permission/healthz
```

确认结构仍为 10；管理员登录、人员与授权、历史日志和策略与备份基线相符。执行一次授权允许和拒绝检查，确认新日志落库；打开**有数据**的数据看板，确认页面正常、图表 JSON 可解析且计数为数字。重启容器并确认挂载配置生效。验收通过后再恢复业务入口并观察错误日志。

## 6. 回滚

本次没有结构迁移，也没有降级迁移。若新镜像验收失败，先停止 1.0.3.2 容器并保持入口关闭，再用保留的 1.0.3.1 镜像和原配置连接同一结构 10 数据库，核对健康、管理员登录及授权后放行。旧容器名若已被占用，先核对并调整名称；不要同时运行新旧应用写入同一库。

如数据本身已损坏，保留故障库供取证，把最终备份恢复到**独立回滚库**，核对旧配置确实指向该库后再启动旧镜像。恢复备份会丢失备份后新增的日志、审计和配置变更，须先保存并制定补录方案。禁止通过手改 `schema_versions` 冒充迁移或回滚。保留旧镜像、备份和日志直到观察期结束。
