# 权限管理系统 1.0.7.1 → 1.0.7.7 升级指南

适用于 Linux x86_64、外部 MySQL 8.x、`docker run` 部署；示例容器名为 `cli-access`，配置目录为 `/opt/cli-access-config`。实际网络、端口、挂载、代理和 TLS 参数应沿用现有部署。本指南不代表生产升级已经执行。CLI 也升级至 1.0.7.7，Windows 安装器同版本重装时仍会替换包内 Wheel，重装和升级保留已选环境及自动保活设置。

## 1. 核对现状与结构

- 上一正式版本：`cli-access:1.0.7.1`，数据库结构 **11**。
- 目标版本：`cli-access:1.0.7.7`，数据库结构 **12**。
- 已比较上一正式标签与目标版本迁移及模型：新增 `notification_clients`、`notification_tasks` 两张表及默认关闭的单用户通知配置。既有管理员、环境（包括默认开通标识）、人员、授权、申请、日志和策略保留；不会自动审批或补发历史申请。必须先显式迁移，再启动新服务，不重新运行 `create-admin`。

在现有数据库查询 `SELECT version FROM schema_versions;`，确认恰有一行且为 11，并核对管理员、人员、授权、日志、申请和策略。若结构不是 11，停止升级，按真实结构及历史指南制定迁移方案；不得手改 `schema_versions`。目标服务健康检查要求结构 12，未迁移不能直接启动。

## 2. 演练、下载与校验

记录当前容器、镜像 ID/摘要、配置目录、网络、端口、数据库连接目标及各表行数。先备份数据库与配置，在**独立测试库**完成恢复演练，再以目标镜像对该测试库显式迁移，核对健康、管理员登录、授权允许/拒绝、日志和有数据的数据看板。演练不得连接生产库。原 `service.env` 及外部 MySQL 保留，不使用附件示例覆盖真实配置。

从 [v1.0.7.7 正式 Release](https://github.com/mossexplore/platform-cli/releases/tag/v1.0.7.7) 下载镜像、`SHA256SUMS`、`manifest.json` 和本指南。核对已下载文件哈希后导入：

```bash
sha256sum --ignore-missing -c SHA256SUMS
docker load -i cli-access-1.0.7.7-linux-amd64.tar.gz
docker image inspect --format '{{.Id}}' cli-access:1.0.7.7
docker image inspect --format '{{index .Config.Labels "org.opencontainers.image.revision"}}' cli-access:1.0.7.7
```

镜像配置 ID、版本和源码提交须与 manifest 一致；文件 SHA256、Docker image ID 和仓库镜像摘要是不同对象。任一校验不符应停止。

## 3. 维护窗口与最终备份

暂停管理台变更和权限检查入口，停止全部 1.0.7.1 实例及其他写入来源。单实例示例：

```bash
docker stop --time 30 cli-access
```

**停止写入后，现在完成最终数据库备份和配置目录备份。** 核对备份文件可读、恢复位置明确，并记录管理员、授权、日志、审计、申请及策略的数量和关键值。确认最终备份可用后才继续迁移。备份失败必须停止升级，不要删除旧容器或镜像。

## 4. 迁移并切换至 1.0.7.7

### 4.1 显式迁移数据库

确认全部写入仍已停止、最终备份已完成、数据库仍为结构 11，再使用目标镜像和原配置目录，由**一个进程**执行迁移：

```bash
docker run --rm -v /opt/cli-access-config:/run/cli-access:ro \
  cli-access:1.0.7.7 python -m app.manage migrate
```

迁移进程沿用实际网络及 TLS 参数；若 MySQL 通过自定义 Docker 网络访问，应使用与原服务相同的网络。不要同时运行多个迁移进程或启动新旧服务写库。MySQL DDL 可能自动提交；表已创建但结构版本未更新时，迁移会检查表是否存在，可在确认备份与状态后重跑。迁移失败时保持停机排查，不能跳过迁移或手改结构版本。

查询 `SELECT version FROM schema_versions;`，确认恰有一行且为 **12**；核对两张通知表存在，`notification_clients` 中 ID 为 1 的默认配置关闭、Token 为空，通知任务表为空；原环境的 `default_grant` 保持不变，人员、管理员、授权、申请、日志和策略与最终备份基线一致。数据核对不通过时不得启动放行。

### 4.2 切换容器

保留已停止的旧容器，给它一个未使用的备份名称：

```bash
docker rename cli-access cli-access-1.0.7.1-backup
```

沿用实际网络、端口和挂载配置；以下仅为单实例示例，启动参数与上一正式版升级指南保持一致：

```bash
docker run -d \
  --name cli-access \
  --restart unless-stopped \
  -v /opt/cli-access-config:/run/cli-access:ro \
  -p 8008:8008 \
  --read-only \
  --tmpfs /tmp:size=64m,mode=1777 \
  --cap-drop ALL \
  --security-opt no-new-privileges:true \
  --log-driver local \
  --log-opt max-size=10m \
  --log-opt max-file=5 \
  cli-access:1.0.7.7
```

端口示例绑定所有网卡，生产应保留现有网络限制与 TLS/Nginx 设置。原管理员账号和配置继续使用，不创建新管理员。

## 5. 验收与放行

保持业务入口关闭，核查容器健康、日志和数据库结构：

```bash
docker inspect --format '{{.State.Health.Status}}' cli-access
docker logs --tail=200 cli-access
curl --fail --max-time 5 http://127.0.0.1:8008/cli-permission/healthz
```

确认结构为 **12**；管理员登录、人员与授权、历史日志、申请和策略与备份基线相符。执行一次授权允许和拒绝检查，确认新日志落库；打开**有数据**的数据看板，确认页面正常、图表 JSON 可解析且计数为数字。核对人员授权页环境标签展开、收起及长名称换行正常，环境别名和时间列完整显示。

### 5.1 启用个人通知与分配助手 Token

**升级完成不等于通知已启用。** 通知默认关闭；未配置 `NOTIFICATION_OWNER_ADMIN_ID` 时，其值为 `0`，侧栏不会显示“个人通知”，即使登录的是超级管理员也一样。当前版本仅支持指定的一位管理员管理助手 Token，不是为所有管理员开放的 Token 分配页面。不使用通知时可跳过本节，不影响原有申请审批流程。

#### 第一步：查询你的管理员 ID

在权限系统实际使用的 MySQL 数据库中执行以下只读查询：

```sql
SELECT id, username, role, enabled FROM admins ORDER BY id;
```

找到你登录管理台使用的 `username`，记录该行的数字 `id`，确认账号已启用（`enabled` 为 1）。这里需要的是 **admins 表中的管理员 ID**，不是账号名、业务用户 ID 或消息接收 UID；不要默认填写 1，也不要重新创建管理员。

#### 第二步：修改服务器原有配置

编辑宿主机 `/opt/cli-access-config/service.env`；该目录按第 4.2 节挂载到容器的 `/run/cli-access`。实际部署使用其他配置目录时，修改当前容器真实挂载的配置文件。

添加或修改以下配置，将占位符替换为上一步查到的数字，文件中只保留一条有效配置：

```dotenv
NOTIFICATION_OWNER_ADMIN_ID=<你的管理员数字ID>
```

保留原数据库连接、Cookie、网关等配置，不用 Release 的示例文件覆盖真实文件。助手 Token、消息接口 auth 和接收 UID 均在本地助手配置，不填写到服务器的 `service.env` 中。

#### 第三步：重启权限服务，使配置生效

这个服务端配置仅在启动时读取，保存文件或刷新浏览器不会立即生效。在当前维护窗口中停止并重新启动同一容器，保留原挂载及启动参数：

```bash
docker stop --time 30 cli-access
docker start cli-access
```

等待容器恢复健康，再执行本节前面的健康检查和日志检查。如果升级后已经恢复业务入口，应另行安排短暂维护窗口执行这一步。无需重新建库、创建管理员或再次迁移。

#### 第四步：进入“个人通知”，生成 Token

使用配置中指定的管理员账号登录。侧栏 **“监控与审计 → 个人通知”** 应出现，也可在权限系统域名后访问路径 `/cli-permission/admin/notifications`。

1. 在“助手凭据”中输入 `reset`，点击 **“生成 / 重置 Token”**。
2. 复制新 Token。它只显示一次，关闭或刷新后无法找回；生成新 Token 会立即撤销旧 Token。
3. 在生成后的 **30 分钟内**完成下一步绑定。丢失或未及时绑定时，重新生成并使用新 Token。

若仍没有入口，依次检查：运行的服务确实为 1.0.7.7、数据库结构为 12、修改的是当前容器挂载的配置文件、配置值与当前登录账号的管理员 ID 一致、修改后已重启。登录其他管理员账号时入口仍会隐藏，直接访问该路径会被拒绝。

#### 第五步：在本地助手绑定并启用通知

从同一 Release 下载独立助手 `permission-notifier-1.0.7.7-windows-source.zip`，按附件 `Notifier-install.md` 安装并启动；需要 Windows、Python 3.12 和可获取 Python 依赖的网络。助手独立安装，不包含在 CLI 安装包中。

1. 在运行助手的电脑浏览器中打开 `http://127.0.0.1:18765`，点击“暂停通知”，保持配置期间暂停。
2. 在“权限系统”中填写权限系统的 HTTPS 服务地址和刚生成的 **助手 Token**，点击 **“保存并应用”**，再点击 **“绑定已保存的 Token”**，确认绑定成功。不要将消息接口的 auth 填到助手 Token 中。
3. 填写消息接口 URL、auth、可选 sender 和启用的接收 UID；每个 UID 会单独调用一次接口。确认真实接口的成功判据后保存，默认“尚未确认”时不会自动发送。
4. 选择测试接收对象，点击“向选中对象发送测试消息”，确认实际收件及逐项结果。这一步会真实发送消息。
5. 返回权限系统“个人通知”，勾选 **“生成新通知并允许领取”**，点击 **“保存设置”**；然后在本地助手点击 **“恢复通知”**。刷新权限系统页面，确认助手在线，并在受控测试中核对新申请的通知记录和收件结果。

历史待审批申请不会自动补发。确需提醒历史申请时，主动点击“补建历史待审批通知”，每次最多补建 100 条尚无通知的待审批申请。关闭本地浏览器不会停止助手，停止发送应使用“暂停通知”或“退出助手”。

### 5.2 通知验收与放行

在独立测试环境使用两个测试接收对象验收：提交申请后入队、逐对象发送、成功对象不重发、失败对象独立处理、回传丢失后的恢复以及撤销 Token 后拒绝访问。生产启用前确认消息接口成功规则；默认未确认时助手不发送。真实测试消息会送达所选对象，应主动操作。升级验收通过后再恢复业务入口并观察错误日志。重启服务并确认原挂载配置生效。

## 6. 回滚

本次涉及结构 **11 → 12**，没有结构 12 → 11 的降级迁移。若新镜像验收失败，先暂停并退出本地助手、停止 1.0.7.7 容器并保持入口关闭。旧版健康检查要求结构 11，**不能只切回 1.0.7.1 镜像连接结构 12 数据库**，也不能手改 `schema_versions` 冒充回滚。

保留故障库供取证，把停写后的结构 11 最终备份恢复到**独立回滚库**，核对原配置确实指向该库，再用保留的 1.0.7.1 镜像和原网络、端口、挂载参数启动。核对健康、管理员登录、人员、授权、原有版本策略及日志后放行。旧容器名若已被占用，先核对并调整名称；不要同时运行新旧应用写入同一库。

恢复备份会丢失备份后新增的通知配置与投递记录、申请审批、授权变更、日志和审计；若已经放行写入，须先保存并明确损失范围及补录方案，再决定回滚。保留旧镜像、最终备份和日志直到观察期结束。

恢复服务端备份不会撤回已发出的消息；保留助手的原 JSON 状态，先核对不确定项和已发送记录，不清空文件以强行重发。恢复生产后重新核对绑定和 Token。
