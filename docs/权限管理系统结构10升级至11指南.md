# 权限管理系统结构 10 升级至 11 指南

本指南用于包含“默认开通环境”功能的目标构建，不代表该构建已正式发布。应使用发布流程验证过的目标镜像摘要；不要覆盖历史镜像标签。

## 结构变化与影响

对比迁移代码，结构 10 → 11 为 `environments` 新增非空布尔列 `default_grant`，数据库默认值为 `0`。现有环境统一关闭，新环境默认关闭；保留人员、环境、授权、管理员和申请记录。无新增权限自动生效，不会自动审批。管理员可在环境管理中开启标识，后续审批只预选已启用的默认环境。

目标应用健康检查要求结构 11，不能直接连接未迁移的结构 10 库。MySQL DDL 可能自动提交；迁移会检查列是否存在，允许列已添加但结构版本尚未更新时重跑。禁止手动修改 `schema_versions` 冒充迁移。

## 1. 升级前演练与准备

确认现有结构为 10；更早结构应先核对完整迁移路径。记录旧镜像摘要、源提交、数据库结构和环境/授权数量。保留原 `service.env`、外部数据库和管理员，不复制示例覆盖真实配置。

备份数据库及配置目录，在独立数据库完成备份恢复演练；用目标镜像迁移并验证登录、授权允许/拒绝、日志、申请审批和默认环境选择。演练不能连接生产数据库。只有验证通过后才安排生产停写。

## 2. 停止写入

停止所有权限服务实例、后台任务与其他数据库写入者，保留旧容器及镜像供回滚。若使用 Compose，在原部署目录停止应用：

```bash
docker compose stop cli-access
```

确认全部写入已停止后，再进入下一步。停止服务不等于完成备份。

## 3. 完成最终备份

按现有 MySQL 运维流程完成停写后的最终数据库备份，记录备份时间、校验结果与存放位置；另外备份配置目录。凭据使用安全配置或交互输入，不写入命令行或日志。

确认最终备份可读取、已完成恢复演练且仍无写入，才允许迁移；备份失败必须停止升级。

## 4. 显式迁移

在原部署配置中将应用镜像指向已验证的目标摘要，保留原数据库地址及配置挂载。只启动一个迁移进程，不同时启动新应用或其他迁移进程：

```bash
docker compose run --rm cli-access python -m app.manage migrate
```

迁移失败时保持服务停止，核对日志与数据库状态，不跳过迁移或手改结构版本。MySQL DDL 已提交但后续步骤失败时，可在确认备份和状态后重跑同一迁移。

## 5. 数据核对与验收放行

核对结构版本为 11、新列存在、所有原环境的 `default_grant` 为关闭，人员、授权、管理员和申请记录与最终备份一致。验收前不恢复正常写入。

```bash
docker compose up -d --wait --wait-timeout 120 cli-access
```

确认健康检查、管理员登录、授权允许/拒绝、日志与有数据的数据看板正常。验证环境标识的保存和回显；仅默认且启用的环境被预选；无默认环境时不预选；快捷按钮可恢复默认、全选与清空；预览后修改默认配置会要求重新核对。通过验收后再放行业务使用。

## 6. 回滚条件与限制

验收失败或数据核对不一致时停止新服务与全部写入，保留故障现场。项目没有结构 11 → 10 的降级迁移，旧应用健康检查要求结构 10，不能只切回旧镜像连接结构 11 库，也不能手改版本号。

需要回滚时恢复停写后的结构 10 最终备份及原配置，再使用原镜像摘要启动并重新验收。恢复备份会丢失备份后产生的默认配置、申请审批、授权变更、日志和审计；若已经放行写入，必须先明确数据损失范围与恢复方案再回滚。
